- 역할 선언

- 전체 워크플로우
- 상태 영속화와 문서 압축

Phase 0~6(환경 구축)이 이미 갖춰진 프로젝트에서, 사람 개입을 최소화하면서도 최상의 품질을 유지하며 자율적으로 프로젝트를 진행하는 전문 에이전트 팀을 구성한다. 팀원 에이전트 정의 파일 형식은 아래 "역할 선언"을 따른다.

## 역할 간 호출 수단 확인 — 이 문서 전체를 적용하기 전에 먼저 확인

아래 모든 설계(지휘자의 판단 금지, 역할 간 직접 소통)는 팀원들이 `SendMessage`로 서로 직접
호출·통지하는 구조를 전제로 한다. 현행 Claude Code에서는 `Agent(name: ...)`로 실행한 이름 있는
에이전트가 세션의 협업 그룹에 자동으로 속하고, `SendMessage`와 공유 작업 목록(`TaskCreate`/
`TaskUpdate`)이 **별도 환경변수 없이** 동작한다. (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 플래그와
`TeamCreate`/`TeamDelete`/`team_name`은 제거된 v1 방식이다. 스킬이나 프로젝트 문서에 남아
있다면 이전 방식의 표현이므로 고친다. 플래그 설정을 지우고, 팀 생성 대신 이름 있는 `Agent` 실행으로 바꾼다.)

따라서 확인할 것은 플래그가 아니라 **각 역할이 실제로 호출 도구를 가졌는지**다. 역할 정의
파일(`.claude/agents/{name}.md`)의 `tools`를 제한했다면 `SendMessage`(와 필요시 `Agent`)가 들어
있는지 확인한다. `SendMessage`, `TaskCreate` 같은 지연 로딩 도구는 `tools`에 적어도 실행 시
빠지는 사례가 보고돼 있으므로, 지속형 팀원에게는 첫 보고에서 실제로 쓸 수 있는 도구 목록을
리더에게 알리게 한다. 빠진 도구가 있으면 지휘자가 그 작업을 대신 처리하거나 `tools` 제한을 푼다.
팀 생성·재구성은 메인 세션(지휘자)이 맡는다.

**모든 역할이 호출 수단을 가진 경우**: 아래 문서를 그대로 적용한다. 각 역할이 실제로
`SendMessage`(와 필요시 `Agent`) 권한을 갖도록 역할 선언 시 명시한다.

**호출 수단을 주지 않기로 한 경우**(안정성 이유로 역할 간 자동 호출을 막거나, 첫 보고에서 도구가
빠진 것이 확인된 경우): 아래 문서의 "역할이 다른 역할에게 말을 건다/직접 알린다" 같은 문구는 실제 SendMessage
호출이 아니라 **지휘자가 그 시점에 그 역할을 실행해야 한다는 트리거 조건 서술**로 재해석한다.
이 경우 "지휘자(메인 세션)의 역할 제한"에 반드시 다음 항목을 추가한다:

> 3. `docs/plans/active/<slug>.md`의 frontmatter(또는 팀원의 보고)가 다음 담당자를 지정하면,
>    지휘자는 판단 없이 즉시 그 담당자를 `Agent` 도구로 실행한다. "누구를 배정할지"는 이미 해당
>    팀원이 결정해 파일에 남긴 것이므로, 지휘자는 그 결정을 실행에 옮기는 기계적 동작만 한다.
> 4. 레드팀·QA/리뷰어처럼 `ReportFindings`만 갖고 Write 권한이 없는 역할이 판정을 남기면,
>    지휘자가 그 판정을 해석·요약 추가 없이 공유 파일에 그대로 옮겨 적은 뒤, 라우팅 매트릭스가
>    이미 정해둔 다음 단계 담당자를 3번에 따라 실행한다.

이 폴백을 Workflow 스크립트로 고정한 방식(추천)은 `workflow-orchestration.md`에 있다.

이는 "판단"이 아니라 이미 내려진 결정의 기계적 집행이므로 지휘자의 판단 금지 원칙과 충돌하지
않는다. 같은 이유로, 어떤 역할이 "사람에게 직접 알린다"고 적어도 실제로는 지휘자(아래 역할
제한 2번)가 그 내용을 그대로 전달해야 한다. 사람과 직접 소통할 도구를 가진 역할이 없기 때문이다.

## 지휘자(메인 세션)의 역할 제한

> 지휘자가 무언가를 판단해야 하는 상황이 생기면, 그것은 설계 결함의 신호다. 그 판단은 팀원 역할로 옮겨야 한다.

지휘자의 역할은 다음 두 가지로 엄격히 제한한다.

1. **팀 구성 (1회성)** — `Agent(name: ...)`로 이름 있는 팀원들을 실행하고, 각 팀원이 `docs/`(기록 시스템)를 스스로 읽고 자기 역할을 파악하도록 연결한다.
2. **사람 요청 중계 (해석 없이 그대로 전달)** — 사용자의 새 작업/요구사항을 분석·해석하지 않고, 공유 백로그(`docs/plans/active/`)에 그대로 기록만 한다.

진행 상황 추적, 에스컬레이션 판단, 병합 승인, 우선순위 결정, 작업 내용 요약·기억은 지휘자가 하지 않는다. 사람에게 알릴 일이 있으면 해당 팀원이 직접 알린다. 이렇게 제한하는 이유는 지휘자의 컨텍스트 사용량이 늘어날수록 할루시네이션 위험이 커지기 때문이다. 지휘자가 아무 내용도 읽거나 판단하지 않으면, 세션이 오래 유지되어도 컨텍스트가 실질적으로 늘어나지 않는다.

## 팀 구성

**고정 코어 역할** (프로젝트 성격과 무관하게 항상 존재):

| 역할 | 책임 |
|---|---|
| QA/리뷰어 | 모든 구현 결과물을 Phase 3 기계적 게이트 + 런타임 증거로 검증, 통과/반려 판정 |
| doc-gardener / archivist | 문서-코드 drift 정리(정확성) + 완료 작업 압축·아카이빙(부피 관리) |
| PRD Maintainer | `docs/prd/` 최신화(기록) + 구현이 PRD 의도와 어긋나는지 확인(정합성) + 신규 요청 트리아지 |

**동적 역할** (Phase 0 진단 결과 + 작업 특성에 따라 그때그때 생성. 도메인·레이어 경계가 다르거나 동시에 고칠 파일이 겹치지 않는 단위로 나눈다):

- **구현자(블루팀)** — 프로젝트 도메인별(예: 프론트엔드/백엔드/인프라)로 필요한 만큼 생성
  - 코드를 구현·수정·리팩터링하는 역할의 정의 본문과 최초 호출 지시에 `karpathy-guidelines`를 읽고 적용하도록 명시한다(`~/.claude/skills/karpathy-guidelines/SKILL.md`). 가정 확인, 최소 구현, 필요한 부분만 변경, 검증 가능한 완료 기준을 도메인 스킬과 함께 사용한다. 기존 스타일과 기존 미사용 코드는 보존하고 자기 변경으로 새로 미사용이 된 코드만 정리한다. 스킬에 접근할 수 없는 담당자에게는 호출 지시에 네 원칙을 포함한다. 역할 파일이나 스킬이 자동 첨부된다고 가정하지 않는다. 코드 리뷰 담당자도 같은 기준으로 diff를 확인하며, 비코딩 역할에는 강제하지 않는다.
- **레드팀** — 품질 전반에서 흠을 찾는 역할(보안 특화 아님). "자율성과 에스컬레이션 기준"에 따라 동적으로 소집

## 역할 선언

역할이 고정이든 동적 생성이든, 생성되는 시점에 다음 네 가지를 반드시 선언한다. 정의 파일은 `.claude/agents/{name}.md`에 두고, 네 항목을 `## 선언` 절에 적는다.

- **목적/책임 범위** — 한 문장
- **트리거 조건** — 언제 활성화되는지
- **입력/출력** — 무엇을 읽고, 무엇을 어디에 남기는지
- **소통 대상 화이트리스트** — 말을 걸 수 있는 대상만 명시, 그 외에는 소통하지 않는다

동적으로 즉석에서 만들어진 역할도 이 선언을 생략하지 않는다. 이 선언이 없으면 팀원들이 정해진 기준 없이 서로의 대화에 참여하게 되고, 이는 각 역할의 컨텍스트를 불필요하게 늘려 지휘자와 같은 할루시네이션 위험을 팀원 레벨에서도 만든다.

## 신규 요청 라우팅과 단계별 소통 매트릭스

지휘자는 사람의 요청을 특정 담당에게 보내지 않고 공유 백로그에 기록만 한다. **PRD Maintainer가 모든 신규 요청의 고정된 첫 반응자(트리아지 담당)**다. `docs/prd/`로 제품 전체 현황을 파악하고 있어 어느 도메인의 일인지 판단하기에 가장 적합하다. PRD Maintainer는 필요한 구현자(들)에게만 말을 건다.

| 단계 | 관여 역할 | 관여 안 함 |
|---|---|---|
| 1. 요구사항 수집 | 사람 ↔ 지휘자 | 전원 |
| 2. 분석(트리아지) | PRD Maintainer(첫 반응) → 구현자 지목 + 레드팀(기준 충족 시, 트리아지 검토) | 그 외 구현자, QA, doc-gardener |
| 3. 설계 | 배정된 구현자(들) + 레드팀(기준 충족 시, 설계 검토) — 설계 단계가 없는 단순 작업은 생략 | PRD Maintainer, doc-gardener |
| 4. 구현 | 배정된 구현자(들) | 나머지 전원 |
| 5. 검증 | 구현자 ↔ QA/리뷰어(항상) + 레드팀(기준 충족 시, 구현 검증) | 관련 없는 구현자, PRD Maintainer, doc-gardener |
| 6. 완료 | QA → PRD Maintainer(갱신 + 정합성 확인) | 구현자, 레드팀 |

레드팀은 이렇게 한 작업 안에서 최대 세 지점(트리아지 검토·설계 검토·구현 검증)에 걸쳐 관여할 수 있다. 구현이 끝난 뒤에 문제를 발견하면 이미 비용이 발생한 뒤이므로, 분석·설계 단계에서 먼저 걸러내는 것이 더 저렴하다.

`doc-gardener/archivist`는 이 표의 어떤 단계에도 실시간으로 참여하지 않는다. 독립된 주기(완료 작업 N개마다 등)로만 동작한다.

## 전체 워크플로우

각 단계에 정확히 누가 관여하는지는 위 소통 매트릭스를 따른다. 여기서는 단계별 내용과 사람 개입 여부만 정리한다.

| 단계 | 내용 | 사람 개입 |
|---|---|---|
| 1. 요구사항 수집 | 사용자가 작업/요구사항을 말함 | **항상 사람과 대화** |
| 2. 분석(트리아지) | 지휘자가 해석 없이 공유 백로그에 기록 → PRD Maintainer가 범위를 정하고 필요한 구현자를 지목 | 없음 (에스컬레이션 기준 해당 시 예외) |
| 3. 설계 | 복잡한 작업은 `docs/design/<기능>.md`에 결정 사항 기록, 배정된 구현자 간 합의 | 없음 |
| 4. 구현 | 블루팀이 Phase 3 기계적 규칙 안에서 작업, `docs/plans/active/`에 진행 기록 | 없음 |
| 5. 검증 | QA/리뷰어(항상) + 레드팀(위 기준에 해당 시) 검증, 실패 시 재작업 반복 | 없음 (반복 한도 초과 시 예외) |
| 6. 완료 | PRD Maintainer 갱신, doc-gardener가 주기적으로 압축 | 없음 |
| 7. 다음 작업 | 백로그의 다음 항목으로, 또는 백그라운드로 넘어가 완료/에스컬레이션 시에만 알림 | 완료/에스컬레이션 알림만 |

## 상태 영속화와 문서 압축

지휘자도 팀원도 대화 기록에 의존하지 않는다. 모든 진행 상태는 파일로 존재한다.

```text
docs/
├── plans/
│   ├── current-state.md    # 현재 상태 한 장 — 세션 재시작의 진입점, 매번 덮어쓴다
│   ├── active/<작업>.md   # 진행 중 작업의 목표·진행상황·의사결정 로그
│   ├── done/                # 완료된 계획 원본 보관 (기본 읽기 경로 밖)
│   └── lineage.md           # 완료 작업의 압축된 이력 (append-only)
├── prd/
│   ├── README.md             # 인덱스 — 섹션별 한 줄 요약 링크
│   ├── <섹션>.md              # 제품 현재 상태
│   └── history.md             # PRD 결정/갱신 이력 (append-only)
└── golden-principles.md      # 코드베이스 전체 규칙 (Phase 5)
```

완료된 작업은 `active/`에서 `done/`으로 옮기고 핵심만 `docs/plans/lineage.md`에 압축 기록한다. `done/`으로 옮기는 것은 완료(6단계) 시점에 PRD Maintainer가 바로 한다. 끝난 계획이 `active/`에 남으면 진행 중 작업으로 오인되기 때문이다. 상세 원본은 `done/`과 git 히스토리에 남지만 팀원의 기본 읽기 경로에서는 빠진다. doc-gardener/archivist가 완료 작업 N개마다, 또는 `active/`의 총 줄 수가 임계치를 넘을 때 이 압축을 수행한다. 결과적으로 팀원이 매번 읽는 활성 컨텍스트는 프로젝트 규모와 무관하게 일정한 크기로 유지된다.

### 세션 재시작의 진입점

지휘자 세션이 끝나 팀을 다시 시작할 때, 새 지휘자는 `docs/plans/current-state.md`(현재 상태 한 장: 지금 단계·다음 할 일·대기 중인 질문, 형식은 harness-engineering 스킬의 `references/checklist.md` Phase 2) 하나만 읽는다. `active/`의 작업 파일 본문은 읽지 않는다.

- **갱신 주체는 팀원이다.** PRD Maintainer가 덮어쓴다. 지휘자는 읽기만 하고, 직접 쓰거나 요약하지 않는다.
- **갱신 시점은 상태가 바뀔 때다.** 작업 배정·완료, 에스컬레이션 발생·해소 시점마다 갱신한다. 팀원은 지휘자 세션이 언제 끝날지 알 수 없으므로, 단일 세션의 "세션을 끝내기 전" 갱신을 이 규칙이 대신한다.
- **"다음 할 일"에 실행할 역할을 적는다.** 예: "구현자(백엔드)를 실행해 `active/<작업>.md` 3단계부터 이어간다." 새 지휘자는 고정 코어 역할과 여기 적힌 역할을 그대로 실행한다. 누구를 실행할지는 팀원이 이미 파일에 적어 둔 결정이므로, 이 실행은 판단이 아니라 팀 구성(역할 제한 1번)을 다시 하는 것이다.
- **"대기 중인 질문"은 지휘자가 해석 없이 사람에게 그대로 전달한다**(역할 제한 2번과 같은 중계).
- **파일이 없거나 실행할 역할이 적혀 있지 않으면** 지휘자는 `active/`를 읽어 추측하지 않는다. 고정 코어 역할만 실행하고, PRD Maintainer가 `active/`를 읽어 `current-state.md`를 다시 쓴다.
- 날짜별 인수인계 파일은 팀 모드에서도 만들지 않는다.

## PRD 관리

`docs/prd/`는 "지금 이 프로젝트가 무엇이고, 어떤 기능이 있고, 어떻게 동작하는지"를 항상 최신 상태로 유지하는 문서다. 400줄 제한 및 인덱스+요약 링크 규칙을 그대로 따른다.

PRD Maintainer가 작업 완료(QA 통과) 시마다:
1. `docs/prd/`의 관련 섹션과 인덱스를 갱신하고
2. 변경 사유를 `docs/prd/history.md`에 append하고
3. 구현이 PRD의 기존 의도·범위와 어긋나 보이면 에스컬레이션(F)으로 올린다

최초 PRD가 없는 기존 프로젝트에서 `docs/prd/`를 처음 만드는 절차는 harness-engineering 스킬의 `references/existing-project-onboarding.md`를 따른다. 소스 코드를 1차 근거로 삼아 도메인 단위 evidence+전수감사 파이프라인으로 생성한다. 이후 들어오는 신규 요청에도 같은 파이프라인을 적용한다.

## 자율성과 에스컬레이션 기준

해당 시 사람에게 알리고, 해당 작업만 보류한 채 팀은 다음 작업을 계속 진행한다.

| 기준 | 내용 |
|---|---|
| A | 보안 경계 변경 (인증/권한/자격증명/네트워크) |
| B | 공개 API·인터페이스 변경 |
| C | 새 외부 의존성 추가 |
| D | 같은 실패가 N회(기본 3회) 이상 반복 |
| E | 아키텍처 경계/레이어 구조 변경 |
| F | PRD 의도와의 불일치 감지 (PRD Maintainer) |
| G | 레드팀·블루팀이 합의 라운드 상한(기본 3회) 안에 합의 실패 |

A의 예외: 하네스 웹 앱 기본값(`127.0.0.1` 바인드, 고정 포트, 기본 경로)을 그대로 따르는 변경은 이미 승인된 기본값이라 A가 아니다. 인증 구현과 외부 공개는 A다(harness-engineering `references/webapp-remote-access.md` 0-2절).

**레드팀 소집 기준:**
- A/B/E에 해당하는 작업은 항상 레드팀 소집
- 그 외에도 "사소하지 않은" 작업(새 기능, 눈에 띄는 로직 변경 등)은 기본적으로 레드팀이 참여한다. 사소한 로컬 수정만 QA/리뷰어 단독으로 처리
- 소집 여부는 트리아지(2단계) 시점에 한 번만 결정되고, 그 작업이 실제로 거치는 체크포인트(트리아지 검토·설계 검토·구현 검증 중 존재하는 것)에 일관되게 적용된다
- 합의 라운드 상한(기본 3회)은 체크포인트마다 독립적으로 적용된다. 상한을 넘기면 그 시점에 바로 에스컬레이션(G)된다
- 하네스 성숙도가 높아질수록(Golden Principles·기계적 게이트가 충분히 쌓일수록) 레드팀 개입 범위는 자연히 좁아진다

## 기술적 제약

Claude Code에서 `Agent(name: ...)`로 실행한 이름 있는 팀원은 그들을 실행한 세션이 살아있는 동안만 존재한다. 따라서 "지휘자가 아예 없다"는 정확히는 불가능하고, "지휘자 세션은 유지되지만 아무 내용도 읽거나 판단하지 않는다"가 실제로 도달 가능한 형태다. 팀 자체가 재구성되어야 하는 경우(새로운 도메인이 필요해 구현자 역할을 새로 만들어야 할 때)에만 지휘자가 다시 `docs/`를 읽고 팀을 재구성한다. 지휘자 세션이 끝나 새 세션에서 팀을 다시 시작하는 경우는 "상태 영속화와 문서 압축"의 "세션 재시작의 진입점"을 따른다. `docs/plans/current-state.md` 하나만 읽는다.
