# Harness Engineering — 에이전트가 안정적으로 작업할 수 있는 저장소 만들기

## 배경과 출처

OpenAI가 2025년 8월~2026년 초까지 5개월간, 수동 코드 작성 0줄로 약 100만 줄 규모의 제품을 Codex 에이전트만으로 만든 경험을 정리한 글 "[Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)"에서 나온 개념이다. 이 스킬은 그 원칙을 Claude Code 환경에 맞게 옮긴 것이다.

## 핵심 철학

**"에이전트가 접근할 수 없는 정보는 존재하지 않는 것과 같다."**

Slack 대화, 사람 머릿속 지식, 문서화되지 않은 관례는 에이전트에게 없는 것이나 마찬가지다. 저장소에 버전 관리되는 형태(코드, markdown, 스키마, 실행 가능한 규칙)로 존재하는 것만 에이전트가 신뢰할 수 있는 유일한 정보원이다.

**"세부 방법을 지시하지 않고, 불변식을 강제해 통제한다."**

에이전트가 무엇을 반드시 지켜야 하는지(예: "경계에서 데이터 형태를 검증해야 한다")는 강제하되, 어떻게 할지(어떤 라이브러리를 쓸지 등)는 자율에 맡긴다. 중앙에서 경계를 강제하고, 그 안에서는 에이전트가 자유롭게 판단하게 한다.

**"산문 규칙은 쉽게 무시된다. 기계적 규칙만 실제로 지켜진다."**

"~하는 것을 선호합니다" 같은 문장은 컨텍스트가 길어지면 묻힌다. 같은 규칙이라도 린터, 훅, 구조 테스트, CI 게이트로 바뀌면 매번 강제된다. 사람이 코드리뷰에서 반복해서 지적하는 항목은 도구로 인코딩해야 한다.

**"문서는 지도이지 1000페이지 매뉴얼이 아니다."**

거대한 단일 지침 파일은 컨텍스트를 낭비하고 곧 실제 코드와 어긋난다. 짧은 진입점(맵) + 필요할 때만 펼쳐지는 깊은 문서 구조(system of record)로 나눈다. `~/.claude/CLAUDE.md`의 "문서 작성" 규칙(400줄 제한, 인덱스 파일 + 요약 링크)이 이 철학을 구현한 예다.

## 언제, 무엇을 하는가

이 스킬이 트리거되면 프로젝트의 현재 성숙도를 먼저 진단하고, 부족한 층(layer)부터 순서대로 구축을 제안한다. 한 번에 모든 Phase를 진행하지 않고, 프로젝트 규모와 사용자 의도에 맞춰 필요한 Phase만 골라 진행한다.

### Phase 0 — 현재 상태 진단

다음을 확인한다.

1. `CLAUDE.md`가 있는가? 있다면 몇 줄인가, 지도 역할을 하는가, 아니면 모든 내용을 담은 긴 매뉴얼인가?
2. `docs/` 디렉토리가 있는가? 설계/아키텍처/계획/기술부채가 구조화되어 있는가, 아니면 산발적인가?
3. 린터, 타입 체커, 구조 테스트, pre-commit/CI 게이트가 있는가?
4. 로그·메트릭·테스트 출력이 사람뿐 아니라 에이전트도 쉽게 읽을 수 있는 형태인가(구조화 로깅, 표준 출력 경로)?
5. PR/코드리뷰에서 반복적으로 나오는 지적(=아직 코드화되지 않은 규칙)이 있는가?
6. 웹 앱이거나 웹 앱 예정인가? 그렇다면 `references/webapp-remote-access.md`(포트·`127.0.0.1` 바인드·기본 경로·인증·Tailscale 외부 접속)를 기준으로 빠진 항목을 진단에 넣는다. 아직 코드가 없는 웹 앱 예정 프로젝트는 그 문서 0-1절에 따라 규칙과 골격 검사를 처음부터 적용한다.

진단 결과를 사용자에게 짧게 보고하고, 아래 Phase 1~8 중 어디서부터 시작할지 합의한다. 상세 체크리스트와 템플릿은 `references/checklist.md` 참조.

**PRD가 없고 과거 작업 기록(설계 문서·실행계획·이슈 기록)은 이미 풍부한 프로젝트**라면 Phase 1로 바로 가지 않는다. Phase 0 완료 직후 소스 코드를 1차 근거로 삼아 PRD를 생성하는 절차를 먼저 거치고, 그 결과(도메인 지도)를 Phase 1 작성에 병행 제공한다. 트리거 조건과 전체 절차는 `references/existing-project-onboarding.md` 참조.

### Phase 1 — 맵 파일 정리 (CLAUDE.md)

- 목표: 100~150줄 내외. "무엇이 어디 있는지" 알려주는 목차 역할만 한다.
- 넣지 않는 것: 상세 아키텍처 설명, 전체 코딩 컨벤션 나열, 긴 설명. 이런 내용은 `docs/`로 옮기고 링크만 남긴다.
- 넣는 것: 빌드/테스트/실행 명령, 핵심 불변식 몇 개, `docs/` 하위 구조로 가는 포인터, 에스컬레이션 규칙(에이전트가 판단하기 어려울 때 어떻게 할지).
- 첫머리에 하네스 버전 표시 `<!-- harness-engineering vN -->`를 둔다(현재 v3). 업그레이드 모드가 이 문자열로 버전을 찾는다.
- 이미 CLAUDE.md가 너무 길면, 내용을 `docs/`로 이관하고 CLAUDE.md는 인덱스로 줄인다. 이는 `~/.claude/CLAUDE.md`의 문서 작성 규칙과 같은 패턴이다.

### Phase 2 — docs/ 기록 시스템(system of record) 구축

에이전트가 필요한 정보를 문서에서 직접 검색해 찾을 수 있는 구조를 만든다.

```text
docs/
├── README.md          # 전체 인덱스 — 각 하위 문서 한 줄 요약 링크
├── architecture/       # 시스템 전체 지도, 도메인/레이어 경계
├── design/              # 개별 기능/컴포넌트 설계 문서 (수락 상태 표시)
├── plans/               # 진행 중 작업 계획 (경량 임시 계획 vs 실행 계획)
│   └── current-state.md # 현재 상태 한 장 — 새 세션의 시작점, 매번 덮어쓴다
└── tech-debt/           # 알려진 부채 목록, 버전 관리됨
```

각 하위 디렉토리에도 인덱스 파일을 두고 요약 링크를 단다. 세부 구조와 템플릿은 `references/checklist.md`.

#### 세션 인수인계 — `docs/plans/current-state.md` 한 장

작업을 새 세션으로 넘길 때, 새 세션이 읽을 "지금 상태"는 `docs/plans/current-state.md` 한 파일에만 둔다. 사용자가 어느 파일을 읽으라고 알려주지 않아도 새 세션이 스스로 이어갈 수 있어야 한다.

- **한 파일을 덮어쓴다.** 날짜별 인수인계 파일(`handoff-<날짜>.md` 등)은 만들지 않는다. 쌓이면 어느 것이 최신인지 알 수 없어, 새 세션이 오래된 "다음 할 일"을 따른다.
- **세 항목만 적는다(60줄 이하).** 지금 단계 / 다음 할 일 / 대기 중인 질문.
- **결정은 링크로만 가리킨다.** 결정 내용은 결정을 기록하는 문서(`docs/design/`, 계획 문서의 의사결정 로그 등)에 한 번만 적는다. 여기에 다시 적으면 한쪽만 고쳐져 서로 어긋난다.
- **갱신 시점은 두 가지다.** 컨텍스트 사용량이 높아져 세션을 나누기로 할 때, 그리고 세션을 끝내기 전. (Phase 7 팀 모드의 갱신 주체와 시점은 `harness-agent-team` 스킬의 `references/team-orchestration.md` "세션 재시작의 진입점"을 따른다.)
- **진입점을 둔다.** `CLAUDE.md` 첫머리에 "새 세션은 `docs/plans/current-state.md`부터 읽는다"는 링크를 둔다.
- **끝난 계획은 `docs/plans/done/`으로 옮긴다.** `docs/plans/active/`에 남아 있으면 새 세션이 진행 중 작업으로 오해한다.

세 문서의 역할은 겹치지 않는다: `current-state.md`는 지금 상태 한 장, `active/<작업>.md`는 진행 중 작업의 상세, `lineage.md`는 완료 작업의 압축 이력이다.

- **멈출 때는 작업을 잃지 않게 한다.** 미커밋 변경은 `wip:` 커밋 하나로 남기고, 작업 트리가 깨진 상태면 커밋 본문에 한 줄로 적는다. push는 하지 않는다.
- **이어받을 때는 기록을 믿는다.** 이전 세션이 끝낸 일을 처음부터 다시 검증하거나 다시 하지 않는다. 다만 "완료"라는 주장은 최종 목표 기준으로 실제 결과물에서 한 번 확인한다.

인수인계 요청만 받았다면 Phase 0 진단을 다시 하지 않고 이 절만 수행한다. 이때 `CLAUDE.md` 진입점 링크나 아래 검사가 아직 없으면 함께 추가한다.

이 규칙은 산문으로만 두지 않고 Phase 3 검사로 강제한다. 템플릿과 검사 예시(`plans-state`)는 `references/checklist.md` 참조.

### Phase 3 — 암묵적 규칙을 기계적 규칙으로 전환

핵심 절차(상세: `references/rule-enforcement.md`):

1. CLAUDE.md, PR 코멘트, 리뷰 기록, 커밋·revert, 사용자가 반복해서 고친 지시에서 실수와 "산문으로만 존재하는 규칙"을 찾는다. 같은 유형이 두 번 나오면 규칙 후보다.
2. 가장 높은 수준에서 고친다. 아키텍처로 없애기 → 타입 → 린트·CI·훅(`PreToolUse`·`PostToolUse`) → 테스트 → 문서 순으로 시도하고, 안 될 때만 아래로 내려간다.
3. 에러 메시지에 "왜 실패했는지"와 "어떻게 고치는지"를 반드시 포함한다. 에이전트가 에러 메시지만 보고 스스로 고칠 수 있어야 한다.
4. 새 검사가 과거의 실제 실수에서 실패하는지 확인한다. 위반이 이미 많으면 늘어난 것만 실패시킨다(점진 강제). 예외는 위반한 줄에 사유·만료일·승인자를 적는다.
5. `CLAUDE.md`에 "규칙 | 강제수단 | 실패를 증명한 사례" 대응표를 둔다. 강제수단이 없는 규칙이 다시 지적되면 같은 변경에서 한 수준 올려 고친다.
6. 훅을 만들 때는 `update-config` 스킬을 사용한다 (파이프테스트 → 실제 트리거 확인까지 포함된 절차 보유).

예시는 `references/checklist.md`의 "약한 규칙 → 강한 규칙 변환 예시" 참조.

### Phase 4 — 런타임 가독성 확보

에이전트가 소스 코드만 보고 판단하지 않고, 실제로 실행해서 확인할 수 있게 만든다.

- 구조화된 로깅(JSON 로그 등)을 쓰고, 에이전트가 관련 로그를 쉽게 필터링할 수 있게 한다.
- 테스트/빌드 실패 메시지가 원인과 위치를 명확히 가리키게 한다.
- UI가 있는 프로젝트라면 브라우저 자동화로 직접 재현·검증할 수 있게 한다. Claude Code의 `run` 스킬(앱 실행/드라이브)이 이 역할을 한다.
- 앱을 실행하고 조작하고 증거를 남기는 방법을 프로젝트 검증 스킬 `.claude/skills/verify-<app>/`로 고정한다(Launch·Doctor·Drive·Evidence·Cleanup 절과 기능 지도). 만들 때 한 번 끝까지 실행해 증명하고, 기능 지도는 Phase 6 루프로 유지한다. 절차는 `references/verification-skill.md`.
- 격리된 작업 환경(git worktree)마다 독립적으로 앱을 실행하고 관찰할 수 있게 하면, 여러 작업을 동시에 안전하게 진행할 수 있다.
- 웹 앱이면 실행 포트·받는 주소(`127.0.0.1`)·기본 경로·인증·외부 접속(Tailscale funnel)과 그 강제수단(골격 검사, 공개 스크립트, guard 훅)을 `references/webapp-remote-access.md`대로 둔다. 인증과 외부 공개는 보안 경계라 사용자가 승인한 계획이 있을 때만 진행한다.

### Phase 5 — Golden Principles 정의

`docs/golden-principles.md`에 코드베이스 전체에 적용되는 소수의(5~10개) 의견 기반 규칙을 적는다. 예:

- "중복 헬퍼 대신 공유 유틸리티를 사용한다."
- "검증 없이 외부 데이터를 그대로 신뢰하지 않는다 (경계에서 파싱)."
- "새로운 의존성 추가는 정당화가 필요하다."

각 원칙은 가능한 한 Phase 3의 절차를 거쳐 린터/구조 테스트로도 강제한다. 문서로만 존재하는 원칙은 곧 잊힌다.

### Phase 6 — Doc-gardening 루프 설정

문서와 코드가 벌어지는 것(drift)을 주기적으로 감지하고 스스로 고치는 순환을 만든다.

- 대상 문서(architecture/design/prd/golden-principles/tech-debt)는 자신이 설명하는 소스/문서 경로를 `covers` frontmatter로 선언하고(`PreToolUse` 훅으로 강제), 별도 인덱스 없이 **git 커밋 시각 비교**만으로 최신성을 판정한다. covers 경로가 문서보다 최근에 바뀌면 "확인 필요", 경로 자체가 없으면 "참조 끊김"으로 표시한다. 정기적으로 실행되는 에이전트(예: `loop` 스킬, 또는 `CronCreate`로 예약)가 이 스크립트를 돌려 리포트를 생성한다. 상세 스크립트는 `references/checklist.md` Phase 6 참조.
- 검증 스킬의 기능 지도 파일(`.claude/skills/verify-<app>/features/*.md`)도 `covers`를 달아 같은 검사 대상에 넣는다.
- 발견하면 작은 수정 PR을 직접 열도록 한다. 1분 안에 리뷰 가능한 크기로 유지한다.
- 대량 정리를 한꺼번에 하지 않는다. 기술 부채는 방치할수록 비용이 커지므로 매일 조금씩 줄이는 편이 낫다.

### Phase 7 — 전문 에이전트 팀 구성과 자율 운영

Phase 0~6이 어느 정도 갖춰진 프로젝트에서, 사람 개입을 최소화하면서 자율적으로 진행하는 전문 에이전트 팀을 구성한다.

**이 Phase는 `harness-agent-team` 스킬을 호출해 진행한다.** 팀 관련 규칙·템플릿은 모두 그 스킬(`~/.claude/skills/harness-agent-team/`)에만 둔다. 이 스킬에는 팀 내용을 다시 적지 않는다. 팀 방식을 고칠 때도 그 스킬만 고친다.

### Phase 8 — PR/리뷰 워크플로우 조정 (선택)

에이전트 처리량이 늘어나면 기존 팀의 병합 관행이 병목이 될 수 있다. 프로젝트에 맞춰 제안한다.

- PR을 작게, 자주 낸다.
- 병합 전 에이전트의 셀프 리뷰 + 추가 서브에이전트 리뷰를 거치게 한다. `superpowers:requesting-code-review`, `code-review` 스킬, 또는 `ralph-loop` 플러그인(자기 검토 반복 루프)을 활용할 수 있다.
- 플레이키 테스트가 전체 진행을 막지 않게 하되, 이는 처리량이 충분히 높은 팀에서만 안전한 트레이드오프임을 사용자에게 알린다.
- Phase 7(전문 에이전트 팀)을 이미 구성했다면, QA/리뷰어와 레드팀이 이 역할의 상당 부분을 대신한다. 이 Phase는 아직 팀을 구성하지 않은 프로젝트에 우선 적용한다.

## 업그레이드 모드 — 기존 프로젝트를 최신 하네스로

이 스킬이 바뀌면 이미 하네스를 적용한 프로젝트도 따라와야 한다. 사용자가 "하네스 업그레이드해줘"라고 하거나, 하네스가 적용된 저장소에서 이 스킬을 쓰는데 버전이 낮으면 이 모드로 간다.

1. `CLAUDE.md`에서 `<!-- harness-engineering vN -->` 문자열을 찾는다. 없으면 v1로 본다.
2. `references/upgrade.md`에서 그 버전 다음부터 현재 버전까지의 변경 항목을 모은다. 항목마다 이미 반영됐는지 확인하는 방법이 있다. 이미 있는 항목은 건너뛴다.
3. 남은 항목 목록을 사용자에게 짧게 보여 주고 승인을 받는다. 프로젝트 이력을 읽어야 하는 항목(규칙 대응표 등)은 따로 표시한다.
4. 승인된 항목을 하나씩 반영하고, 프로젝트 검사를 통과시킨 뒤 항목마다 커밋한다(push 금지).
5. 마지막으로 버전 표시를 현재 버전으로 바꿔 커밋한다.
6. 에이전트 팀이 구성된 프로젝트(`.claude/workflows/team-run.js`가 있음)면 `harness-agent-team` 스킬의 업데이트 모드도 이어서 진행한다.

## 진행 원칙

- **한 번에 모든 Phase를 진행하지 않는다.** Phase 0 진단 후, 프로젝트에 가장 부족한 1~2개 Phase부터 제안하고 사용자 승인을 받는다.
- **일반화한다.** 예시 코드는 프로젝트의 실제 언어/프레임워크에 맞춰 새로 작성한다. 특정 언어(Elixir 등)에 고정된 규칙을 그대로 복사해 쓰지 않는다.
- **작은 산출물로 나눈다.** CLAUDE.md/문서 파일은 `~/.claude/CLAUDE.md`의 400줄 규칙을 그대로 따른다.
- **강제가 곧 신뢰다.** 문서에만 적어둔 규칙은 지켜지지 않는다고 가정하고, 가능한 모든 규칙을 기계적 검사로 승격하는 것을 기본값으로 삼는다.
