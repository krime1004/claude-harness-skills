# 기존 프로젝트 최초 온보딩 — PRD 없음 + 과거 문서 있음

## 언제 사용하는가 (트리거)
표준 **Phase0(진단) 완료 직후**, 다음 조건을 모두 만족하는 프로젝트에 이 절차를 쓴다.
- PRD가 없다.
- 과거 작업기록(설계 문서·실행계획·이슈 기록 등)과 소스 코드는 이미 존재한다.
- `harness-engineering`을 이 프로젝트에 처음 적용한다.

이 문서는 "착수 방식"만 다룬다. Phase0~8 각 단계의 상세 실행은 `references/checklist.md`를 그대로 따른다.

## Phase 로드맵 상 위치
표준 Phase0(진단) → **PRD생성단계 1~2**(준비+스코프 발견, 아래) → 그 결과(도메인 지도)를 표준 **Phase1**(CLAUDE.md 맵) 작성에 병행 제공 → 도메인 단위로 **PRD생성단계 3~7** 반복 → 큐 소진 시 **8**(정상 운영)로 전환, 이후 표준 Phase2 이후 작업과 독립적으로 유지보수한다.

내부 단계 이름은 표준 Phase0~8과 번호가 겹치지 않도록 별도 이름공간 "PRD생성단계 1~8"을 쓴다. Phase7(전문 에이전트 팀)·Phase8(PR 워크플로우)은 항상 마지막으로 미룬다. PRD생성단계와 covers frontmatter 검증만 Phase 번호와 무관하게 Phase0 직후부터 계속 작동한다.

## PRD생성단계 1~8
1. **준비**: origin diff 확인(변경 발견 시 보류·보고·승인 후 재개), 기존 문서 인벤토리 작성(목록만, 삭제 없음), 하네스 팀 안정화 재확인, 진행 상태 추적 파일 생성.
2. **스코프 발견**: 아래 "범용성 — 3단계 폴백"으로 경계를 정하고, 별도 import 그래프로 leaf-first 순서를 확정한다.
3. **증거 수집**: 소스·관련 문서·테스트·git log를 모은다. `which gh && gh auth status`로 확인되면 PR 설명을 보조 증거로 추가하고, 안 되면 자동으로 건너뛴다. 둘 다 정상 경로다. 인증 없는 API 직접 호출·웹 크롤링은 근거 오염 방지를 위해 금지한다. 세부 추출 기법은 `references/prd-extraction-techniques.md` 참조.
4. **초안 작성**: 원자적 문장(주장 1개) + 근거 인용(파일:줄, 또는 문서 파일:줄)으로 쓴다. 문서만 근거인 후보는 아래 "레거시 문서의 역할 한정" 규칙에 따라 본문에 들어가지 못한다. 세부 기법은 `references/prd-extraction-techniques.md` 참조.
5. **전수 감사**: 신규 서브에이전트(fork 아님)를 감사자로 호출한다. 새 서브에이전트는 이전 대화를 모르는 상태로 시작하므로 추가 엔지니어링 없이 작성 근거로부터 독립적이다. 감사 프롬프트에는 대상 문장 + 인용된 근거만 전달하고 작성 의도는 포함하지 않는다. 감사자는 원문을 직접 열람해 근거 존재와 의미적 일치를 확인하고, 근거가 문서라면 그 서술이 현재 소스 코드의 실제 동작과도 일치하는지까지 확인한다.
6. **교정**: 기계적으로 명백한 stale 서술(경합 근거 없음)은 코드를 진실로 채택하고 문서에는 stale 플래그만 남긴다(원본 미삭제). 두 근거가 실제로 상충하면 한쪽을 임의로 택하지 않고 "충돌 — 사람 판단 필요" 절에 나란히 남긴다. 스코프당 문장수 상한 초과는 상한을 늘리지 않고 즉시 하위 스코프로 재귀 분할한다(내용 누락 금지).
7. **도메인 완료 처리**: 스코프가 아니라 도메인 경계마다 커밋+보고한다. 초기 2~3개 도메인은 명시적 승인을 받고, 이후는 opt-out(중단 요청 없으면 계속 진행)으로 전환한다. 5개 이상 파일을 건드리는 도메인 커밋은 착수 전 origin diff를 재확인하고, 변경 발견 시 보류·승인 후 재개한다.
8. **정상 운영**: 초기 큐 소진 후 신규 모듈은 델타만 재적용한다. doc-gardening 정기 재검토는 평소 구조적 재확인(인용 좌표 유효성)만 실행하고, 의미 이탈 신호가 있을 때만 무거운 전수 재감사를 재트리거한다. cron/CI로 구현한다(훅은 도구 호출 시에만 동기 실행되므로 정기 스윕에는 쓸 수 없다).

신규 기능 요청도 같은 파이프라인을 탄다: 표준 Phase7에서 PRD Maintainer 역할이 확정된 뒤 들어오는 신규 요청은 그 기능의 설계 문서·PR을 근거 삼아, 8단계 "정상 운영"의 델타 재적용과 동일하게 PRD에 새 스코프로 추가한다.

## 범용성 — 스코프 경계 3단계 폴백
1. 기존 소스 디렉터리 경계를 그대로 채택한다.
2. 디렉터리가 평평하거나 일관되지 않으면 import 그래프 클러스터링을 쓴다. 언어별 표준 import/require 구문을 정규식이나 해당 언어 파서로 추출해 자체 의존 그래프 스크립트를 만든다. 외부 클러스터링 도구 설치가 불확실하면 즉시 3단계로 넘어간다.
3. (무정형 예외) 파일을 알파벳순 고정 크기 배치(5~8개)로 잘라 "flat 모드"로 표기한다. 이후 스코프가 누적되면 재군집을 검토한다.

leaf-first 순서는 경계를 어느 단계로 정했든(3단계 flat 모드 포함) 항상 별도로 import 그래프를 계산해 정한다.

스코프당 문장수 상한(예: 40개)을 넘으면 상한을 늘리지 않고 하위 스코프로 재귀 분할한다. 도메인(스코프 발견에서 나온 최상위 그룹 1개)당 스코프 수 상한(예: 5개)도 동일 로직을 적용한다. 상한을 넘는 그룹은 여러 도메인으로 나눈다. 이로써 "프로젝트 전체 = 도메인 1개"는 구조적으로 불가능해진다.

## 레거시 문서의 역할 한정
레거시 문서(설계 스펙·실행계획·이슈 기록 등, 소스 코드가 아닌 것)는 PRD 내용을 단독으로 결정하지 않는다.

- 1차 근거는 항상 소스 코드(또는 테스트)다. 레거시 문서는 후보 발굴(어디를 볼지 힌트)과 교차확인(코드 근거와 나란히 대조)에만 쓴다. 문서 근거만 있고 대응하는 코드 근거가 없는 후보는 4단계 초안 작성에서 본문에 들어가지 못하고, `unreviewed-backlog.jsonl`과 같은 자리에 "문서전용-미확인"으로 표시한다.
- 5단계 전수 감사는 항상 코드 기준으로 판정한다. 근거가 문서인 문장은 "문서와 문장이 일치하는가"뿐 아니라 "그 문서 내용이 현재 코드의 실제 동작과도 일치하는가"까지 확인한다. stale이면 6단계 규칙대로 코드를 진실로 채택한다.
- 스코프 완료 이후, 레거시 문서 원본은 삭제하지 않고 보존되지만 능동적 참조 대상에서는 빠진다. 필요할 때(과거 의사결정 배경 확인 등) 예외적으로 열람하는 참고자료이며, 완료된 PRD 내용이나 이후 판단에 계속 영향을 주는 활성 입력은 아니다.

이 항목을 이 문서에 두는 이유는, 4단계(초안 작성)뿐 아니라 5단계(감사)·6단계(교정)·완료 이후 참조 정책까지 PRD생성단계 전체에 걸쳐 반복 적용되는 상시 규칙이기 때문이다. 반대로 신호 추출의 구체적 패턴·AST 기법은 3~4단계 실행 중에만 필요해 `prd-extraction-techniques.md`로 분리했다.

## "100% 일치"의 정의
완료(전수 감사 통과)된 스코프에 한해, 모든 문장이 실재하는 근거를 갖고 그 근거와 의미적으로 정확히 일치함을 뜻한다. 미완료 스코프는 PRD에 아예 존재하지 않는다(자리채움 없음). 이는 "불완전함"과 "부정확함"을 구조적으로 분리하는 장치다. 최초 완료 판정은 항상 무거운 전수 감사로만 내리고, 완료 후에는 doc-gardening이 구조적 100%(인용 좌표 유효성)만 상시·저비용으로 재확인한다. 근거끼리 실제로 상충하는 경우는 별도 conflict 절로 분리되므로, 완료 스코프의 100% 보장(conflict 절 제외 영역)을 훼손하지 않는다.

## 레거시 보존 / 원격 diff / 서브에이전트 권한
- 레거시 원본은 하네스 팀 안정화 전까지 삭제하지 않는다(stale·conflict로 플래그된 문서도 예외 없음). 재배치는 `git mv`만 쓰고, 이 재배치도 5개 이상이면 원격 diff 확인 대상이다.
- doc-gardening cron/CI 스윕은 표준 Phase6이 정식 착수되면 그 체계로 흡수되는 임시 대체물이다.
- covers frontmatter는 Write(PreToolUse가 전체 내용 검사)/Edit(PreToolUse가 치환을 재구성 후 검사)을 구분해 강제하고, PRD 섹션 frontmatter에 스코프명·증거 소스·감사 상태(draft/gated/complete/conflict)·문장수를 기록한다.
- PRD생성단계 3~7의 모든 서브에이전트는 읽기 전용(쓰기 없음)으로 제한한다. CLAUDE.md·안전 지도가 아직 없는 시점에 다수 서브에이전트가 코드베이스를 탐색하지만, 쓰기 권한이 없으면 안전 지도 부재가 실질적 리스크로 이어지지 않는다. 쓰기(PRD 파일 생성/수정, 커밋)는 오케스트레이터만 6~7단계에서 수행한다.

## 과거 작업 기록을 docs/ 표준 구조에 편입하기
전체 재구조화 계획을 먼저 세우지 않는다. 4단계로 나눈다.

1. **즉시 (승인 불필요)**: 기존 문서 폴더는 그대로 두고, 최상위 인덱스 파일(`docs/README.md`)만 추가해 현재 상태 지도를 만든다.
2. **Phase0 진단 시 측정**: 토큰 비용은 문서 크기 × 세션 로그의 Read 호출 빈도로 추정한다(세션 usage 필드는 턴 전체 값이라 특정 문서에 직접 귀속시키지 않는다). 오답 사례는 과거 로그 샘플링 + 대표 질문 재현 실험으로 확인한다. 데이터 확보에 실패하면 Phase1(CLAUDE.md 지도화)을 fallback으로 채택하고, "데이터 기반 결정"이 아니라 "fallback"으로 명시적으로 라벨링한다.
3. **국소 조치**: 확인된 pain point 한 곳만 손댄다. 기본 동작은 원본 파일 이동·삭제 금지다. deprecated 마킹은 원본 위치에 frontmatter 태그만 추가하고 인덱스에서 참조한다. 데이터가 특정 파일의 분할·이동을 구체적으로 지목한 경우만 승인 라운드 + 원격 diff 확인을 거쳐 `git mv`로 수행한다(삭제 아님).
4. **반복**: 조치 하나가 끝날 때마다 승인받고 다음으로 넘어간다. 동시에 5개 이상 파일/문서를 건드리는 대규모 변경 착수 전에는 반드시 원격과의 diff를 먼저 확인한다.

## 단일 대형 파일과 문서-현실 괴리(drift) 처리
- **즉시 예외**: 명백히 거짓인 한 줄 서술(사실 확인이 100% 명확하고 고치는 비용이 거의 0)은 바로 수정한다.
- **파일 비대화**: 위 "과거 작업 기록 편입"과 동일한 측정 방법론+fallback을 적용해 병목이 실측되면 분할하되, 이동 시에도 동일한 승인+원격 diff 절차를 따른다.
- covers frontmatter 강제와 그 2차 방어선(`git commit` 가로채 스테이징 검사, 표준 경로 밖 우회는 못 막음)은 위 "레거시 보존" 절과 동일하다.

## Phase 순서 결정 원칙 (비-PRD 사안)
- Phase0(진단)이 유일한 고정 시작점이다.
- 우선순위 원칙: "데이터가 있으면 데이터가 가리키는 곳, 데이터가 없거나 불충분하면 fallback(Phase1)." Phase1 추천은 별도 경쟁 원칙이 아니라 이 fallback 규칙의 한 사례다.
- Phase0 완료 후 나온 pain point 우선순위에서 1개만 골라 다음 Phase를 진행하고, 승인받은 뒤에야 다음을 고른다. 대규모 변경 착수 전 원격 diff 확인은 특정 Phase에 묶이지 않는 공통 선행조건이다.

## 인정하는 한계
- `gh` CLI 유무·인증 상태는 환경마다 다르다. 이 절차는 없어도 정상 동작하지만, 있는 환경에서는 증거 코퍼스가 더 풍부해질 수 있다.
- "이전 대화를 모르는 상태로 시작"하는 컨텍스트 격리는 신규 서브에이전트 호출만으로 보장되지만, "특정 파일/경로 접근 자체를 차단"하는 하드 격리는 기본 제공 기능이 아니다. 5단계 감사자에게는 이에 의존하지 않고 읽기 전용 권한 + 좁혀진 입력만 전달한다.
- Phase0 실측(오답 재현 실험 등)은 과거 세션 로그가 남아있어야 성립한다. 로그가 없으면 fallback(Phase1)으로 시작한다.
- 오버플로우로 인한 확신도 순위 정렬(신호 확신도 순 + 하위 스코프 재귀 분할)은 블루팀 서브에이전트 자신의 판단이라 항상 정확하지는 않다. 실제로 대기열(다음 스코프로 미뤄진 후보)에 확신도가 더 높은 항목이 섞여 있는 경우가 확인됐다. 5단계 감사자에게는 채택된 문장뿐 아니라 오버플로우로 밀려난 후보 목록도 함께 검토해, 순위가 명백히 잘못된 항목은 이번 스코프로 승격하도록 지시한다.
- 같은 소스 코드에 같은 절차를 다시 적용해도 서브에이전트의 판단(문장 분할 방식·화이트리스트 신호의 Tier 분류)이 매번 동일하게 재현되지는 않는다. 이는 결함이 아니라 LLM 기반 서브에이전트의 본질적 한계다. 따라서 doc-gardening 재감사에서 "예전 실행 결과와 문장 수·Tier가 다르다"는 사실 자체는 stale 판정 근거로 쓰지 않는다. 판정은 항상 현재 코드와의 의미적 일치 여부만 기준으로 한다.
