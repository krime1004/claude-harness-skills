# 웹 앱 기본 규칙 — 로컬 실행·인증·외부 접속(Tailscale)

웹 앱이거나 웹 앱 예정인 저장소에 하네스를 적용할 때 쓴다. SKILL.md Phase 0(진단)과 Phase 4(런타임 가독성), 업그레이드 v2 → v3(`upgrade.md`)가 이 문서를 가리킨다. `<...>`는 프로젝트마다 채운다. 프레임워크 이름은 예시다.

목표: 웹 앱은 이 컴퓨터에서 실서버로 실행한다. 허가된 사용자는 Tailscale을 설치하지 않고 `https://<기기>.<tailnet>.ts.net/<프로젝트명>/`으로 접속해 로그인 뒤 사용한다. 그 밖의 경로로는 접속할 수 없다.

적용 범위:
- 새 프로젝트(웹 앱 코드가 아직 없거나 막 시작함): 0절 규칙과 골격 검사를 처음부터 적용한다. 1~10절은 해당 코드가 생길 때 함께 적용한다.
- 기존 웹 앱 프로젝트: 한꺼번에 적용하지 않는다. Phase 0 진단 결과에 이 문서의 빠진 항목을 우선순위 후보로 올리고, 사용자가 승인한 것만 하나씩 적용한다. 이미 다르게 정해진 것은 바꾸기 전에 묻는다.

## 0. 적용 시점과 승인 기준

### 0-1. 웹 앱 코드가 없어도 먼저 적용한다
하네스를 먼저 깔고 웹 앱은 나중에(에이전트 팀의 조각 등으로) 만드는 경우가 있다. 규칙이 없으면 프레임워크 기본값(경로 `/`, `0.0.0.0`, 포트 3000)으로 만들어지고, 나중에 경로·주소를 일괄 변경해야 한다.
- Phase 0 진단에서 "웹 앱이거나 웹 앱 예정인가"를 묻는다. 예정이면 코드가 없어도 10절의 규칙 표 줄과 안내 문서를 먼저 넣는다.
- 프로젝트의 검사 명령(없으면 `scripts/check-all.sh`를 만든다)에 웹 앱 골격 검사를 넣는다. 같은 명령을 pre-commit 또는 CI에서도 실행한다.
- 골격 검사는 2절 구조 테스트까지 처음부터 포함한다. 프레임워크가 없으면 통과하고, 프레임워크 설정 파일(예: `next.config.*`, `vite.config.*`, `nuxt.config.*`, `svelte.config.*`)이 생기면 자동으로 아래를 검사한다:
  - 기본 경로 설정이 `/<프로젝트명>`인가.
  - 실행 스크립트(`dev`·`start` 등)에 `127.0.0.1` 바인드와 고정 포트가 있는가.
  - 소스에 기본 경로 없이 쓴 앱 절대 경로가 없는가(2절 구조 테스트).
- 그러면 프레임워크를 설치하는 조각 자체가 검사에서 실패하므로 그 조각 안에서 설정을 끝내게 된다. 팀이 검사를 새로 만들거나 바꿀 필요가 없다(검사 변경은 팀 보류 기준이다).
- 에이전트 팀이 있으면 `.claude/agents/prd-maintainer.md`에 적는다: "웹 앱 골격 조각이면 완료 기준에 '웹 앱 기본 규칙 1·2절 적용, 골격 검사 통과'를 넣는다." 강제수단은 골격 검사이고, 이 줄은 미리 알려 주는 역할이다.

### 0-2. 보안 경계 승인 기준
- 1·2절 기본값(`127.0.0.1` 바인드, 고정 포트, 기본 경로)을 그대로 따르는 변경은 이미 승인된 하네스 기본값이다. 보안 경계 변경으로 보고 멈추지 않는다.
- 3절(프록시 주소 판단), 4절(인증 구현), 6·7절(외부 공개)은 보안 경계 변경이다. 사용자가 승인한 계획(`docs/plans/active/<작업>.md`, 요청에 사용자 원문으로 승인)이 있을 때만 진행한다. 에이전트 팀도 같다.
- 인증 라이브러리(argon2·bcrypt, OAuth 등)는 새 외부 의존성이다. 계획에 미리 적어 승인받는다. 그렇지 않으면 팀은 그 조각을 보류한다.

## 1. 포트와 받는 주소
- 3000·5173·8080처럼 다른 프로젝트와 겹치기 쉬운 포트를 쓰지 않는다.
- 개발 서버와 실서버(빌드 후 실행)는 서로 다른 고정 포트를 쓴다. 두 서버를 동시에 실행할 수 있어야 한다. 예: 개발 `<N>`, 실서버 `<N+1>`.
- 정하기 전에 `lsof -i :<포트>`로 비어 있는지 확인한다.
- 모든 서버(개발·실서버·e2e 테스트 서버)는 `127.0.0.1`에서만 받는다. `0.0.0.0`(모든 네트워크)에서 받지 않는다. 그래야 LAN IP나 Tailscale IP로 포트에 직접 들어오는 경로가 생기지 않는다.
- 포트와 받는 주소는 실행 스크립트(`package.json`의 `dev`·`start` 등)에 적는다. 예: Next.js `next start -H 127.0.0.1 -p <N+1>`, Vite `vite --host 127.0.0.1 --port <N>`. 프레임워크 기본값이 `0.0.0.0`일 수 있으므로 반드시 명시한다.
- 문서·eval·검증 안내의 주소도 같은 포트로 맞춘다.

## 2. 경로: 앱은 `/<프로젝트명>` 아래에서 실행된다
- 한 호스트에 여러 프로젝트를 경로로 등록하므로, 앱 기본 경로를 `/<프로젝트명>`으로 둔다(예: Next.js `basePath`, Vite `base`). localhost에서도 같은 경로를 쓴다.
- 코드에 앱 경로(`/api/...`, `/login`, 폼 `action`, `fetch` 주소, 리디렉션 대상)를 직접 적지 않는다. 프레임워크의 경로 도우미나 기본 경로 상수를 거친다.
- 쿠키 `Path`는 기본 경로로 둔다. 경로를 바꾸면 예전 경로(`Path=/`) 쿠키도 로그아웃 때 지운다.
- 쿠키 이름에 프로젝트 접두사를 붙인다(예: `<프로젝트명>_session`). 같은 호스트의 프로젝트들은 같은 origin이라 쿠키 `Path`로는 서로 격리되지 않는다.
- Tailscale은 `/<프로젝트명>`과 `/<프로젝트명>/`을 리디렉션 없이 그대로 넘긴다. 끝 슬래시 처리는 앱(프레임워크)이 한다.
- 강제수단: 0-1절 골격 검사에 포함된 구조 테스트(기본 경로 없이 쓴 앱 절대 경로 찾기), 그리고 기본 경로 아래에서 로그인·주요 화면을 여는 e2e.

## 3. 프록시 뒤 주소: 허용 목록으로만 믿는다
- 외부 접속은 Tailscale 프록시 뒤에서 들어온다. Tailscale은 `Host`를 공개 이름 그대로 넘기고 `X-Forwarded-Host`·`X-Forwarded-Proto`·`X-Forwarded-For`를 직접 채운다(클라이언트가 보낸 값은 덮어씀). 443에서는 포트가 붙지 않는다(`<기기>.<tailnet>.ts.net`). 다른 프록시나 같은 컴퓨터의 다른 프로세스가 보낸 요청은 다를 수 있으므로 아래 규칙을 그대로 둔다.
- OAuth 돌아올 주소·리디렉션·쿠키 `Secure` 판단의 기준 origin은 `X-Forwarded-Proto`와 `X-Forwarded-Host`로 만든 `<proto>://<host>`를 쓴다. 단 이 값이 환경 변수 허용 목록(`APP_ORIGINS`, 쉼표 구분)의 항목과 문자열이 정확히 같을 때만 쓴다. 아니면 요청 주소를 쓴다.
- 머리글에 값이 여러 개(`a, b`)이거나 한쪽이 없으면 믿지 않고 요청 주소를 쓴다.
- `APP_ORIGINS`에는 `https://<기기>.<tailnet>.ts.net`(포트 없음)을 넣는다. 빠지면 redirect_uri가 요청 주소 기준으로 만들어져 `redirect_uri_mismatch`가 난다.
- 이 판단은 한 함수(예: `appOrigin(req)`)에만 두고, 로그인 시작·콜백·로그아웃·인증 리디렉션이 모두 그것을 쓴다.
- 테스트: 허용 목록에 있는 값, 없는 값, 여러 값, 머리글 누락, proto 불일치(http 머리글인데 목록은 https), 포트·경로가 붙은 값.

## 4. 인증과 접근 허가
외부 공개(funnel) 주소는 인터넷 누구나 열 수 있다. 앱 인증이 유일한 방어선이다. 이 절의 구현은 0-2절에 따라 사용자 승인 계획이 있을 때 진행한다.
- 로그인 방식은 두 가지다: 구글 로그인, 자체 아이디·비밀번호.
- 접속 허가는 웹 앱의 사용자 관리 화면에서 지정한 계정만 받는다. 허가 목록은 DB에 둔다(환경 변수 아님. 바꿀 때마다 재시작하지 않게).
- 구글 로그인에 성공해도 허가 목록에 없으면 거부한다.
- 로그인하지 않으면 모든 경로(API 포함)를 막는다. 공개 경로는 허용 목록(로그인 화면, 로그인 처리, 상태 점검 등)으로만 둔다.
- 비밀번호는 느린 해시(argon2·bcrypt 등)로 저장한다. 평문·가역 암호화 금지.
- 로그인 시도 횟수를 계정·IP별로 제한한다.
- 첫 관리자 계정은 화면이 아니라 로컬 명령이나 환경 변수로 만든다. 첫 접속자가 관리자가 되는 방식 금지.
- 상태 점검 경로는 내부 정보(버전, 환경 변수 이름·설정 여부, 오류 상세)를 보여 주지 않는다. 비로그인 응답은 `{"ok":true}` 수준으로 둔다.
- Tailscale 머리글은 참고만 하고 인증 대신 쓰지 않는다: funnel 요청에는 `Tailscale-Funnel-Request: ?1`이 붙고 `Tailscale-User-Login`은 없다(클라이언트가 보낸 값은 지워짐). tailnet 요청에는 `Tailscale-User-Login`이 붙는다.
- 강제수단: 공개 경로 허용 목록 밖의 모든 라우트가 비로그인 요청에 401/리디렉션을 반환하는지 확인하는 테스트, 허가 목록에 없는 계정의 로그인 거부 테스트, 상태 점검 응답에 허용한 키 밖의 값이 없는지 확인하는 테스트.
- 이 절과 3절은 레드팀 검토 대상이다(열린 리디렉션, 머리글 조작, 인증 우회, 무차별 대입, 허가 목록 우회).

## 5. OAuth 리디렉션 주소 (구글 기준)
- 구글 OAuth 등록은 사용자가 프로젝트마다 직접 한다. 하네스는 등록할 주소 목록만 10절의 안내 문서에 적는다(`<콜백 경로>`는 프로젝트의 OAuth 콜백 라우트):
  - `http://localhost:<개발 포트>/<프로젝트명>/<콜백 경로>`
  - `http://localhost:<실서버 포트>/<프로젝트명>/<콜백 경로>`
  - `https://<기기>.<tailnet>.ts.net/<프로젝트명>/<콜백 경로>`
- 구글은 http 리디렉션을 localhost에만 허용한다. 외부 접속은 https 주소가 필요하다.
- 등록 확인은 앱 로그인 시작 주소를 따라가 구글 응답에 `redirect_uri_mismatch`가 없는지로 본다. 등록하지 않은 포트로 대조군을 함께 확인한다.
- 127.0.0.1과 localhost는 다른 주소다. 로컬 로그인은 등록한 이름(localhost)으로만 접속한다.

## 6. Tailscale 외부 접속
- 사전 조건: Tailscale 관리 콘솔에서 HTTPS 인증서와 이 기기의 funnel 사용 권한(tailnet 정책의 `funnel` 노드 속성)이 켜져 있어야 한다. 확인: `tailscale status --self --json`의 `CapMap`에 `funnel`과 `https://tailscale.com/cap/funnel-ports?ports=443,...`가 있다.
- 실서버만 등록한다. 개발 서버는 등록하지 않는다(localhost에서만 쓴다).
- 443 포트 하나만 쓰고, 프로젝트는 경로로만 등록한다. 443 이외 포트(8443, 10000 등)에는 serve/funnel을 열지 않는다. 그래서 `https://<기기>.<tailnet>.ts.net:<포트>` 형식으로는 접속할 수 없다.
- 호스트 루트 `/`와 등록하지 않은 경로는 Tailscale이 404를 반환한다. 루트에는 아무것도 등록하지 않는다.
- 경로 등록과 해제는 7-1절의 공개 스크립트(`scripts/expose-tailscale.sh`)로만 한다. `tailscale serve`·`tailscale funnel`을 직접 실행하지 않는다. 스크립트가 쓰는 명령:
  - 등록: `tailscale funnel --bg --https=443 --set-path /<프로젝트명> http://127.0.0.1:<실서버 포트>/<프로젝트명>`
  - Tailscale은 마운트 경로를 제거하고 나머지를 대상 URL 뒤에 이어 붙인다(쿼리 유지). 그래서 대상 URL에 `/<프로젝트명>`을 다시 포함해야 앱이 기본 경로를 받는다.
- funnel은 포트 단위로 켜진다(`AllowFunnel["<호스트>:443"]`). 443에 funnel을 켜면 443에 등록된 모든 프로젝트가 함께 공개된다. 그래서 443에 등록하는 앱은 모두 하네스를 적용한 앱이고 4절(인증과 접근 허가)을 갖춰야 한다. 앱마다 공개 범위를 다르게 할 수 없다.
- serve/funnel 설정은 시스템 전체 설정이다. 다른 프로젝트의 경로를 지우지 않는다. `tailscale serve reset`과 `tailscale funnel --https=443 off`(포트의 모든 경로를 뗌, Tailscale이 화면에 안내하는 명령)는 쓰지 않는다.
- 명령 문법은 Tailscale 버전마다 다를 수 있다(실측: 1.102.4). 적용 전에 `tailscale funnel --help`로 확인한다.
- macOS 앱 설치면 CLI가 PATH에 없을 수 있다: `/Applications/Tailscale.app/Contents/MacOS/Tailscale`.
- 접속 조건: 이 컴퓨터가 켜져 있고, Tailscale과 실서버가 실행 중이어야 한다. funnel은 대역폭 제한이 있다.

## 7. 공개 전 검사와 강제
인증이 없거나 `0.0.0.0`에서 받는 앱은 외부에 공개되지 않게 막는다. 실서버 실행 자체가 아니라 공개(funnel 등록) 단계에서 막는다. `127.0.0.1`에서만 받는 서버는 인증이 없어도 이 컴퓨터 밖에서는 열리지 않기 때문이다.

### 7-1. 공개 스크립트 `scripts/expose-tailscale.sh`
- 위치와 이름은 모든 프로젝트에서 같게 둔다. 설정값(프로젝트명, 실서버 포트, 상태 점검 경로, 보호 경로 목록, 공개 경로 목록)은 스크립트 맨 위 변수로 둔다.
- 설정 읽기는 `tailscale serve status --json`으로 한다: 포트는 `TCP`의 키, 경로는 `Web["<호스트>:<포트>"].Handlers["<경로>"].Proxy`, 공개 여부는 `AllowFunnel["<호스트>:<포트>"]`.
- `on`(등록)은 아래 순서로 검사하고, 하나라도 실패하면 등록하지 않고 이유를 출력한 뒤 0이 아닌 값으로 끝난다:
  1. 실서버가 떠 있는지: `http://127.0.0.1:<실서버 포트>/<프로젝트명>/<상태 점검 경로>`가 200.
  2. 받는 주소: `lsof -nP -iTCP:<실서버 포트> -sTCP:LISTEN`의 모든 줄이 `127.0.0.1:<포트>`다. `*:<포트>`·`0.0.0.0`·`[::]`가 있으면 실패.
  3. 인증 확인(비로그인 요청): 보호 경로 목록, API 경로, 임의 경로(`/<프로젝트명>/__probe_<난수>`)가 모두 401이거나 로그인 화면으로 리디렉션(302·303·307·308)이다. 200이면 실패.
  4. 공개 경로 목록은 비로그인으로 200이어도 된다. 단 응답에 내부 정보가 없어야 한다(4절 상태 점검 규칙). 상태 점검 응답에 허용한 키 밖의 값이 있으면 실패.
  5. 기존 설정: `TCP`에 443 이외 포트가 있으면 실패. 같은 경로에 다른 대상이 등록돼 있으면 실패. 443에 이미 등록된 다른 경로가 있으면 "funnel을 켜면 함께 공개된다"고 경로 목록을 출력한다.
- 검사를 통과하면 6절의 등록 명령으로 등록하고, 8절의 외부 항목을 확인해 결과를 출력한다. funnel을 켠 직후 약 1분간 외부 TLS 연결이 실패할 수 있으므로(실측 `SSL_ERROR_SYSCALL`) 외부 확인은 20초 간격 5회까지 재시도한다.
- `off`(해제)는 아래 순서로 한다:
  1. 이 프로젝트의 경로만 해제한다: `tailscale funnel --https=443 --set-path /<프로젝트명> off`.
  2. 443에 다른 경로가 남아 있으면 `AllowFunnel`이 켜진 채 남는다(실측). 이때는 남은 경로와 "funnel이 켜져 있다"는 사실만 안내하고 다시 등록하지 않는다. 남은 경로를 `tailscale serve`로 다시 등록하면 443 전체가 tailnet 전용이 되어 다른 프로젝트의 공개까지 꺼지기 때문이다. 다른 프로젝트에 영향을 주지 않는다. 이 프로젝트의 경로는 1단계에서 해제했으므로 외부에서 접속되지 않는다.
     - 443에 남은 경로가 없으면 `AllowFunnel`도 함께 사라진다(실측). 따로 할 일이 없다.
  3. `serve status --json`을 다시 읽어 내 경로가 없고 결과가 의도대로인지 출력한다.
- 실제 응답을 보는 검사라 프레임워크와 상관없이 동작한다. 소스 코드를 읽어 인증 유무를 판단하지 않는다.

### 7-2. Claude Code 훅 `.claude/hooks/guard-tailscale.sh`
- 에이전트가 공개 스크립트를 건너뛰지 못하게 한다. PreToolUse(Bash) 훅으로 아래를 막는다:
  - `tailscale serve`·`tailscale funnel` 직접 실행(`status`·`--help`는 허용).
  - 서버 실행 명령에서 `0.0.0.0` 바인드(`-H`·`--host`·`--hostname`·`HOST=` 뒤의 `0.0.0.0`).
- 훅은 `update-config` 스킬 절차(파이프 테스트 → 실제 트리거 확인)로 만들고 등록한다. 아래 코드와 설정은 예시다. `jq`가 있는지 먼저 확인한다(macOS 15 이상 기본 포함).

  ```bash
  #!/usr/bin/env bash
  # PreToolUse(Bash): tailscale serve/funnel 직접 실행과 0.0.0.0 바인드를 막는다.
  cmd=$(jq -r '.tool_input.command // ""')
  ts='(^|[/[:space:];&|(])tailscale[[:space:]]+(serve|funnel)([[:space:]]|$)'
  ok='tailscale[[:space:]]+(serve|funnel)[[:space:]]+(status|--help)'
  if printf '%s' "$cmd" | grep -Eiq "$ts" && ! printf '%s' "$cmd" | grep -Eiq "$ok"; then
    echo "tailscale serve/funnel 직접 실행 금지. scripts/expose-tailscale.sh 를 쓴다." >&2
    exit 2
  fi
  if printf '%s' "$cmd" | grep -Eq '(-H|--host|--hostname|HOST=)[= ]?0\.0\.0\.0'; then
    echo "0.0.0.0 바인드 금지. 127.0.0.1 을 쓴다." >&2
    exit 2
  fi
  exit 0
  ```

  ```json
  {
    "hooks": {
      "PreToolUse": [
        {
          "matcher": "Bash",
          "hooks": [
            { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard-tailscale.sh" }
          ]
        }
      ]
    }
  }
  ```

- 훅 자체 테스트(예: `.claude/hooks/guard-tailscale.test.sh`)를 두고 프로젝트 검사 명령(`check-all.sh` 등)에 연결한다. 그래야 훅이 고장 나도 pre-commit·CI에서 잡힌다(실측 약 0.1초). 아래 명령을 훅에 넣어 결과를 확인한다:
  - 차단: `tailscale funnel --bg --set-path /x http://127.0.0.1:1/x`, `/Applications/Tailscale.app/Contents/MacOS/Tailscale serve --bg ...`, `cd app && tailscale serve reset`, `next start -H 0.0.0.0`, `HOST=0.0.0.0 npm start`.
  - 통과: `tailscale serve status`, `tailscale funnel --help`, `scripts/expose-tailscale.sh on`, `next start -H 127.0.0.1`.

### 7-3. 공개를 누가 실행하나
- 공개(`scripts/expose-tailscale.sh on`)는 사용자가 명시적으로 지시할 때만 메인 세션이 실행한다. 지시가 있어도 7-1절 검사를 통과해야 공개된다.
- 에이전트 팀은 공개하지 않는다. 팀 실행은 사람에게 묻지 않고 끝까지 진행하므로 공개 직전에 확인받을 지점이 없다.
- 팀의 외부 접속 확인(8절)은 이미 공개된 경우에만 한다. 확인을 위해 먼저 공개하지 않는다.

### 7-4. 한계
- 사람이 터미널에서 `tailscale funnel`을 직접 실행하는 것은 막을 수 없다. "등록은 공개 스크립트로만"을 CLAUDE.md 규칙 표에 적어 사람도 따르게 한다.
- 훅은 Claude Code 에이전트가 실행하는 명령에만 걸린다. 명령을 변수에 담아 실행하거나 설정 파일에 `0.0.0.0`을 쓰는 경우는 훅이 잡지 못한다. 이 경우는 7-1절 검사 2(`lsof`)가 잡는다.

## 8. 접속·차단 확인
설정 뒤 아래를 모두 확인한다. 실패 항목이 있으면 끝난 것이 아니다.
- 이 컴퓨터에서 외부(funnel) 경로를 확인하는 방법: 공개 DNS로 중계 IP를 찾고(`dig +short <기기>.<tailnet>.ts.net @1.1.1.1`) `curl --resolve <기기>.<tailnet>.ts.net:443:<중계 IP> https://...`로 요청한다. 그냥 요청하면 MagicDNS가 tailnet 경로로 보내 funnel을 확인하지 못한다.
- 열려야 하는 것:
  - 외부 경로로 `https://<기기>.<tailnet>.ts.net/<프로젝트명>/<상태 점검 경로>`가 200.
  - `/<프로젝트명>`과 `/<프로젝트명>/` 둘 다 로그인 화면으로 간다(리디렉션 반복 없음).
  - 로그인 시작 주소의 redirect_uri가 Tailscale 주소다.
  - 사용자 확인: Tailscale을 끈 외부 기기(휴대폰 LTE 등)에서 로그인까지 된다.
- 막혀야 하는 것:
  - `lsof -nP -iTCP:<포트> -sTCP:LISTEN` 결과가 `127.0.0.1:<포트>`다(`*:<포트>`면 실패).
  - 다른 기기에서 `http://<LAN IP>:<포트>`와 `http://<Tailscale IP>:<포트>`가 연결 거부(사용자 확인).
  - `tailscale serve status --json`의 `TCP`에 `443`만 있다.
  - `https://<기기>.<tailnet>.ts.net/`(루트)가 404.
  - 비로그인 상태로 보호 경로·API를 열면 401 또는 로그인 화면.
  - 상태 점검 응답에 내부 정보가 없다.
  - 허가 목록에 없는 계정으로 로그인하면 거부.

## 9. 실서버 운영 주의 (프레임워크에 따라 해당하면)
- 실서버는 코드를 바꿔도 반영되지 않는다. 변경 뒤 다시 빌드·재시작한다. 세션이 메모리에 있거나 빌드마다 비밀값이 바뀌면 사용자에게 로그인이 풀렸을 수 있다고 알린다.
- e2e가 자체 빌드를 하면 실행 중인 실서버의 빌드 폴더를 덮어쓸 수 있다. e2e 빌드 폴더를 따로 두거나(예: Next.js `distDir`를 환경 변수로), e2e 뒤 실서버를 다시 빌드한다.
- 빌드 때 정적으로 만들어질 수 있는 상태 점검 라우트(예: Next.js 14 이하 GET 핸들러)는 실행 시점 값을 읽도록 동적으로 둔다.
- 환경 변수 파일(예: `.env.local`)은 서버 시작 때만 읽힌다. 빌드 때 굳는 값(예: Next.js `NEXT_PUBLIC_*`, 기본 경로 설정)은 바꾸면 다시 빌드해야 한다.

## 적용할 때 사용자에게 물을 것

0. 웹 앱인지, 아직 코드는 없지만 웹 앱 예정인지(예정이면 0-1절에 따라 규칙과 골격 검사를 먼저 적용한다)

5. 첫 관리자 계정을 만드는 방법(로컬 명령 또는 환경 변수)
6. 인증 구현(4절)을 지금 계획으로 세울지(0-2절: 보안 경계라 승인 계획 필요)
