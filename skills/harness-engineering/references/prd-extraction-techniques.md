# 소스 코드 기반 정책 추출 기법

PRD생성단계 3(증거 수집)·4(초안 작성)에서 소스 코드로부터 정책 후보를 뽑아내는 세부 기법이다. 트리거 조건과 전체 흐름은 `references/existing-project-onboarding.md` 참조.

## 기본 구조 — 화이트리스트형 신호 추출
분기문·검증 애너테이션·유효성검증 스키마·enum/상태머신·설정값/flag·도메인예외·테스트assertion·DB제약·태그된 주석(`// POLICY:`류), 이 9종 신호 각각에 화이트리스트 패턴을 정의하고 매칭되는 것만 근거 후보로 삼는다.

매칭 안 되는 것은 배제하되 버리지 않고 스코프별 `unreviewed-backlog.jsonl`에 쌓는다. 재현율보다 정밀도를 우선하므로, "PRD에 없다고 그 도메인에 정책이 없는 건 아니다"라는 한계를 도메인 완료 보고에 매번 명시한다.

## 신호 2단계 분류
- **Tier 1 (자동 확정)**: `// POLICY:` 태그, 프레임워크 표준 권한 데코레이터, feature flag 호출처럼 마커가 명시적이고 모호하지 않은 신호. AST 쿼리로 후보 = 결론.
- **Tier 2 (후보 생성만)**: enum 비교+상태 대입, 설정값 비교처럼 구조는 AST로 잡히지만 정책 여부 판단이 필요한 신호. AST가 후보를 뽑고, PRD생성단계 4(초안 작성) 시점에 서브에이전트가 정책 여부를 확정한다. "AST 매칭 = 최종 분류"로 서술하지 않는다.

## 화이트리스트 버전 관리
화이트리스트 자체도 covers frontmatter 대상이다. 완료된 스코프의 frontmatter에 `whitelist_version`을 기록한다. 화이트리스트가 확장되면 doc-gardening 스윕이 구버전으로 완료된 스코프를 재감사 후보로 표시한다.

도메인 완료 보고에는 "이번 도메인에서 백로그로 쌓인 신호 건수"를 함께 적는다 — PRD생성단계 7(도메인 완료 처리)의 opt-out 자동진행 중에도 화이트리스트 확장 판단이 보고 사이클에 자연히 얹히게 하기 위해서다.

## 오버플로우 처리
화이트리스트 통과 후보만으로도 스코프당 문장수 상한을 넘으면, 신호 확신도 순(상태전이·권한분기 → 스키마제약 → 설정/flag → 예외·DB제약 → 테스트 → 태그주석)으로 정렬해 상한만큼만 이번 스코프에 채택한다. 나머지는 내용 누락 금지 원칙에 따라 하위 스코프로 재귀 분할한다.

## 테스트 근거 병기
문장에 소스 근거와 함께, 있으면 테스트 근거도 병기해 PRD생성단계 5(전수 감사)의 비용을 낮춘다.

- **Python**: `coverage.py`의 `dynamic_context = test_function` 설정(CLI 플래그가 아니라 `.coveragerc`/`pyproject.toml`의 `[run]` 섹션 설정 키)으로 분기→테스트의 정확한 매핑이 가능하다.
- **JS/TS**: 이에 대응하는 네이티브 기능이 없다. 정확한 매핑이라 과장하지 않고 "조건에 쓰인 식별자·에러 메시지를 테스트 파일에서 텍스트로 찾는 느슨한 근접성 확인"으로만 표시한다.

## 전수 감사 보완 (Tier 2 대상)
신규 서브에이전트 감사는 기본적으로 "인용 좌표가 실재하고 문장과 의미가 맞는지"만 본다. Tier 2처럼 정책 여부 판단이 들어간 문장은 감사 지침에 "좌표 확인뿐 아니라 그 판단 근거(왜 정책으로 확정했는지)도 재확인"하라는 절차를 추가한다.
