# Phase 4 — 프로젝트 검증 스킬 만들기와 유지하기

에이전트가 실제 앱을 띄우고, 사용자처럼 조작하고, 증거를 남기는 방법을 프로젝트 안의 스킬로 고정한다. 그러면 "앱에서 확인해" 가 매번 설명 없이 실행할 수 있는 단계가 된다.

출처: cursor/plugins의 pstack `skills/create-verification-skill/SKILL.md`와 `skills/maintain-verification-skill/SKILL.md`를 Claude Code 경로에 맞게 옮겼다.

## 만들기

### 1. 사용자가 아니라 저장소에 묻는다

코드에서 답을 찾고, 관찰할 수 없는 것만 사용자에게 묻는다.

| 질문 | 확인할 것 |
| --- | --- |
| 표면 | 사용자가 실제로 만지는 것: 웹 UI, CLI/TUI, 데스크톱 앱, API, 모바일, 라이브러리. 여럿이면 주 표면을 고르고 나머지는 적어 둔다 |
| 실행 | 저장소의 dev 명령(package scripts, Makefile, README), 포트, 환경 변수, 시드 데이터, 인증 |
| 조작 | 기존 하네스 먼저(Playwright 스펙, expect 스크립트, curl 가능한 엔드포인트, 디버그 포트). 없을 때만 일반 방법: 웹·Electron은 브라우저/CDP, CLI는 tmux/PTY, 서비스는 HTTP |
| 관찰 | 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태 |
| 격리 | 두 인스턴스를 나란히 띄울 수 있는가(포트, 데이터 디렉터리, 프로필). 안 되면 스킬에 그렇게 적는다 |

체크아웃이 그대로는 빌드·실행되지 않으면 먼저 고치거나 정확히 보고한다. 깨진 기반에서 쓴 스킬은 틀린 단계를 가르친다.

### 2. 스킬 생성

`.claude/skills/verify-<app>/SKILL.md`를 쓴다. frontmatter에 `name: verify-<app>`과 `description`(앱 이름, 표면, 언제 쓰는지)을 넣는다. 아래 절을 모두 저장소에서 찾은 실제 값으로 채운다. 자리표시자를 남기지 않는다.

- **Launch:** 검증용 실행 명령과 준비 완료 신호(로그 줄, 프롬프트). 빈 데이터 디렉터리에서 마이그레이션·시드까지 거쳐 사용 가능한 상태가 되어야 한다. "프로세스가 응답함"은 준비 완료가 아니다. 종료 방법도 적는다.
- **Doctor:** "이 인스턴스를 조작해도 되는가"에 답하는 읽기 전용 점검 하나. 프로세스, 빌드 버전, 포트 소유, 인증. 이상해 보이면 항상 이것부터 돌린다.
- **Drive:** 이 저장소의 실제 선택자·명령. 좌표나 탭 순서보다 안정적인 손잡이(ARIA 라벨, data 속성, 프롬프트 문자열, 라우트)를 쓴다.
- **Evidence:** 무엇을 어디에 남기는지. 실제 사용자 경로를 쓰고 테스트 전용 엔드포인트는 쓰지 않는다. 최종 화면만이 아니라 동작과 결과 상태를 함께 남긴다. 화면 밖 부수효과(파일, DB 행, 보낸 메시지)도 확인한다. dry-run이 정말 무엇을 건너뛰는지는 관찰해서 확인한다.
- **Cleanup:** 이번 실행이 띄운 것만 종료한다. 프로세스 이름으로 죽이지 않는다. 증거 파일은 지우지 않는다.
- **Helpers:** 스킬이 포함한 스크립트는 실행 가능하게 두고, 호출 방법을 본문에 적는다.

### 3. 기능 지도 시드

`.claude/skills/verify-<app>/features/README.md`(인덱스)와 사용자 기능마다 파일 하나를 만든다. 처음에는 라우트, 명령, 메뉴, 문서에서 찾은 상위 3~5개면 된다. 각 파일은 사용자 관점으로 네 개의 H2를 갖는다.

```markdown
---
covers:
  - src/features/<기능>/
---
# <기능 이름>

## Sub-features
## How to get to it (user POV)
## Driving it with <harness>
## Gotchas
```

시드 데이터에 전제 조건이 없어 경로가 실패하면, 실패로 보고하고 이유를 `Gotchas`에 적는다. 통과시키려고 경로를 약하게 만들지 않는다.

### 4. 넘기기 전에 한 번 실행한다

생성한 스킬의 지시대로 Launch → Doctor → 기능 하나 Drive → Evidence → Cleanup을 실행한다. Cleanup 뒤에도 증거가 지정 위치에 남아 있는지 확인한다. 실패하면 고치고, 실패한 시도마다 Cleanup도 돌린다. 한 번도 실행하지 않은 스킬은 초안이다.

대역(실제 대상 대신 컨테이너, 원격 대신 로컬)에서 증명했다면, 대역이 해 주고 실제 대상은 해 주지 않을 설정 단계를 모두 적는다.

## 유지하기

기능 지도는 앱이 바뀌는 순간 낡는다. Phase 6 doc-gardening 루프에 이 점검을 넣는다.

- **드리프트 감지:** 기능 파일의 `covers` frontmatter로 `scripts/check-doc-drift.sh`가 그대로 "확인 필요"를 표시한다(`checklist.md` Phase 6).
- **점검 절차:**
  1. 인덱스 정리. 빠지거나 남는 항목, 죽은 링크를 고친다.
  2. 소스 읽기. 기능 파일마다 읽기 전용 서브에이전트 하나를 병렬로 띄운다. 각자 소스 기준 동작 요약, 드리프트 의심(인용 포함), 실행 검증 방법 하나를 돌려준다. 앱을 조작하거나 파일을 고치지 않는다.
  3. 실행 점검. 소스가 깨끗해 보여도 반드시 한다. 조작은 메인 세션 하나가 맡는다. 모든 기능을 한 번 이상 실행한다. 처음 조작 전과 실패한 조작 뒤에는 Doctor를 다시 돌린다.
  4. 분류. 설명이 틀림 → 지도 수정. 동작은 맞는데 하네스가 못 움직임 → 하네스 수정. 앱이 실제로 깨짐 → 제품 회귀로 사용자에게 보고하고, 문서로 덮지 않는다.
- **결과는 셋 중 하나:** `clean`(고칠 것 없음), `changed`(증명된 수정만 커밋 하나), `blocked`(막힌 이유를 정확히).
- **수정 범위:** 검증 스킬 디렉터리 안만 고친다. 제품 코드는 고치지 않는다.
