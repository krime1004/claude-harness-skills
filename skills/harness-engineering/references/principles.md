# Harness Engineering — 배경 개념 정리

## 출처

OpenAI 공식 블로그 "[Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)" (openai.com/index/harness-engineering/). 직접 크롤링이 차단되어 있어, InfoQ 보도, Martin Fowler의 리뷰 글, 리더 프록시를 경유해 원문 전체를 확인했다. 이 문서는 OpenAI 원문의 개념만 정리한 것이며, 특정 언어/프레임워크(Elixir 등)에 고정된 세부 구현은 원문에 없는 내용이므로 포함하지 않았다 — 실제 적용 시 프로젝트의 언어/스택에 맞게 새로 설계해야 한다.

## 왜 이 개념이 나왔는가

OpenAI 팀은 2025년 8월부터 5개월간 빈 저장소에서 시작해 수동 작성 코드 0줄로 약 100만 줄, 약 1,500개 PR을 Codex 에이전트만으로 만들었다. 초기에는 속도가 예상보다 느렸는데, 원인은 에이전트의 역량 부족이 아니라 **환경이 충분히 정의되지 않았기 때문**이었다. 이후 엔지니어의 역할이 "코드를 직접 짜는 것"에서 "환경을 설계하고, 의도를 명시하고, 에이전트가 신뢰할 수 있는 작업을 하도록 피드백 루프를 구축하는 것"으로 바뀌었다.

이때 만든 환경 전체를 **harness(하네스)**라고 부른다 — 강하지만 예측 불가능한 말을 원하는 방향으로 이끄는 고삐·안장에서 따온 비유다.

## 핵심 용어

| 용어 | 의미 |
|------|------|
| Harness | 에이전트가 신뢰성 있게 작업하도록 만드는 환경 전체 — 문서 구조, 아키텍처 제약, 관찰성, 훅/린터, 병합 정책 등을 포함 |
| CLAUDE.md (원문 OpenAI 글의 AGENTS.md에 해당) | 저장소의 짧은 지도. 약 100줄 내외로, 더 깊은 문서로 가는 포인터 역할만 한다 |
| System of record | `docs/` 같은, 버전 관리되는 구조화된 지식 저장소. 여기 없는 지식은 에이전트에게 없는 것과 같다 |
| Golden Principles | 코드베이스 전체에 적용되는 소수의 의견 기반 기계적 규칙 |
| Doc-gardening | 문서와 코드의 불일치(drift)를 주기적으로 스캔해 자동으로 작은 수정 PR을 여는 백그라운드 프로세스 |
| Taste invariants (미학 불변식) | 로깅 형식, 명명 규칙, 파일 크기 등 스타일 관련이지만 기계적으로 강제되는 규칙 |
| Runtime legibility (런타임 가독성) | 에이전트가 소스 코드뿐 아니라 실제 실행 중인 시스템(로그/메트릭/UI)을 관찰해 스스로 검증할 수 있는 상태 |
| Ralph Wiggum Loop | 에이전트가 자신의 PR을 스스로 리뷰하고, 추가 에이전트 리뷰를 받아 만족할 때까지 반복하는 자기 검토 구조. Claude Code의 `ralph-loop` 플러그인이 이와 유사한 패턴을 구현한다 |

## 간단한 성숙도 참고 (원문 기반, 단순화)

원문은 명시적인 단계 모델을 제시하지 않지만, 서술된 진행 과정을 정리하면 대략 다음과 같은 흐름이다. 프로젝트가 지금 어디쯤 있는지 가늠하는 용도로만 쓰고, 반드시 순서대로 갈 필요는 없다.

1. **비정형 단계** — 에이전트에게 매번 프롬프트로 설명, 반복 불가능
2. **저장소 지침 단계** — CLAUDE.md는 있지만 산문 규칙 위주, 길고 정리 안 됨
3. **재현 가능한 실행 단계** — 빌드/테스트가 한 명령으로 재현 가능, 문서는 구조화되기 시작
4. **기계적 강제 단계** — 린터/구조 테스트/훅으로 핵심 규칙이 강제됨
5. **런타임 가독성 단계** — 에이전트가 로그/UI/관찰성 도구로 직접 검증 가능
6. **자가 유지보수 단계** — doc-gardening, 자기 검토 루프 등으로 엔트로피를 스스로 관리

Phase 0 진단(`checklist.md` 참조) 결과를 이 단계에 대략 대응시켜, 다음에 투자할 곳을 정한다.

## 흔한 안티패턴

- **CLAUDE.md에 모든 것을 욱여넣기** — 컨텍스트가 혼잡해지고, 정작 중요한 규칙이 묻힌다.
- **산문 규칙만 쓰고 끝내기** — 기계적으로 강제되지 않으면 결국 지켜지지 않는다.
- **"컨텍스트는 많을수록 좋다"는 착각** — 관련 없는 정보가 많으면 오히려 판단을 오염시킨다.
- **컴파일/테스트만 통과하면 됐다고 여기기** — 구조적으로 불필요한 모듈, 중복 추상화, 과도한 공개 API는 별도로 점검해야 한다.
- **런타임 증거 없이 구조만 검증하기** — 코드는 정상이어도 실제 실행 동작이 다를 수 있다.
- **모든 변경을 같은 속도로 병합하기** — 보안 경계, 런타임 토폴로지 변경 같은 것은 더 신중한 경로를 거쳐야 한다.
- **몰아서 정리하기** — 기술 부채는 매일 조금씩 갚는 편이 안전하다. 대량 정리는 확장되지 않는다.

## 이 개념을 오해하지 않기

이 프레임워크는 "AI가 알아서 다 하게 두라"는 뜻이 아니다. 정반대로, **사람이 하던 판단(어디까지 자율을 줄지, 무엇을 강제할지, 무엇을 승인받아야 하는지)을 도구와 구조로 명시적으로 인코딩하는 작업**이다. 원문도 "여전히 규율이 필요하지만, 그 규율이 코드가 아니라 스캐폴딩(환경 구축)에서 드러난다"고 강조한다.
