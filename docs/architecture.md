# 설계 결정과 트레이드오프

이 문서는 두 스킬의 주요 설계 결정을 정리합니다. 결정마다 해결하려는 문제, 선택한 방식, 검토한 대안, 감수한 비용을 적습니다. 세부 절차는 각 스킬의 `SKILL.md`와 `references/`에 있습니다.

## 설계 전제

- **기여자는 모두 에이전트라고 가정합니다.** 에이전트는 자기가 연 파일만 보고, 가장 가까운 예시를 복사하고, 컴파일되는 가장 짧은 길을 택합니다. 그래서 파일 하나만 보고 맞아 보이는 변경이 저장소 전체에서도 맞도록 설계합니다.
- **에이전트가 접근할 수 없는 정보는 존재하지 않는 것과 같습니다.** 저장소에 버전 관리되는 형태(코드, Markdown, 스키마, 실행 가능한 검사)로 있는 것만 신뢰합니다.
- **자율은 경계 안에서만 줍니다.** 무엇을 지켜야 하는지는 강제하고, 어떻게 할지는 맡깁니다.

## 하네스(harness-engineering)

### 1. 지도와 기록 시스템의 분리

| 항목 | 내용 |
| --- | --- |
| 문제 | 지침 파일 하나에 모든 규칙을 넣으면 컨텍스트를 낭비하고, 중요한 규칙이 묻히고, 쉽게 낡습니다. |
| 결정 | `CLAUDE.md`는 100~150줄의 목차로 둡니다. 상세 내용은 `docs/` 아래 주제별 문서에 두고, 디렉터리마다 한 줄 요약 링크를 담은 인덱스를 둡니다. |
| 대안 | 단일 대형 지침 파일. 작성은 쉽지만 규모가 커지면 에이전트가 필요한 부분을 찾지 못합니다. |
| 비용 | 문서 수가 늘어 유지 비용이 생깁니다. 이 비용은 결정 3(문서 최신성 검사)으로 관리합니다. |

### 2. 규칙 강제 사다리와 실패 증명

| 항목 | 내용 |
| --- | --- |
| 문제 | "~를 선호한다" 같은 산문 규칙은 컨텍스트가 길어지면 지켜지지 않습니다. 리뷰어가 같은 실수를 반복해서 잡게 됩니다. |
| 결정 | 같은 유형의 실수가 두 번 나오면 규칙 후보로 봅니다. 아키텍처, 타입, 린트·CI·훅, 테스트, 문서 순으로 가장 높은 수준에서 막습니다. 새 검사는 과거의 실제 실수를 되살려 실패하는 것을 확인한 뒤에 채택합니다. |
| 보완 | 위반이 이미 많으면 기준 파일을 두고 늘어난 위반만 실패시킵니다(점진 강제). 예외는 위반한 줄에 사유, 만료일, 승인자를 적습니다. `CLAUDE.md`에 "규칙 / 강제수단 / 실패를 증명한 사례" 대응표를 둡니다. |
| 대안 | 문서화와 코드 리뷰. 비용은 낮지만 에이전트 처리량이 늘면 리뷰가 병목이 됩니다. |
| 비용 | 검사를 만드는 초기 비용이 큽니다. 에러 메시지에 실패 이유와 고치는 방법을 적어야 하므로, 검사 하나의 작성 비용도 커집니다. |

### 3. `covers` 선언과 git 시각 비교로 문서 최신성 판정

| 항목 | 내용 |
| --- | --- |
| 문제 | 문서가 코드와 어긋나도 아무것도 실패하지 않습니다. 낡은 문서는 에이전트에게 잘못된 지시가 됩니다. |
| 결정 | 대상 문서는 자신이 설명하는 경로를 `covers` frontmatter로 선언합니다. 선언은 `PreToolUse` 훅으로 강제합니다. 최신성은 git 커밋 시각만으로 판정합니다. 담당 경로가 문서보다 최근에 바뀌면 "확인 필요"이고, 경로가 없으면 참조가 깨진 것입니다. |
| 대안 | 별도 인덱스나 해시 데이터베이스. 더 정밀하지만 인덱스 자체를 유지해야 하고, 그 인덱스가 또 낡습니다. |
| 비용 | 사소한 코드 변경에도 "확인 필요"가 뜹니다. 판정이 보수적인 대신 추가 상태가 없습니다. |

### 4. 세션 인계는 파일 한 장을 덮어쓴다

| 항목 | 내용 |
| --- | --- |
| 문제 | 날짜별 인계 파일이 쌓이면 어느 것이 최신인지 알 수 없습니다. 새 세션이 오래된 "다음 할 일"을 따르게 됩니다. |
| 결정 | `docs/plans/current-state.md` 한 파일을 덮어씁니다. 지금 단계, 다음 할 일, 대기 중인 질문 세 항목만 60줄 이하로 적습니다. 결정 내용은 다시 적지 않고 링크로만 가리킵니다. 형식은 검사로 강제합니다. |
| 보완 | 진행 중 작업의 상세는 `plans/active/<작업>.md`에, 완료 이력은 `plans/lineage.md`에 둡니다. 세 문서의 역할은 겹치지 않습니다. |
| 비용 | 과거의 인계 상태는 git 이력에서만 볼 수 있습니다. |

### 5. 런타임 가독성과 프로젝트 검증 스킬

| 항목 | 내용 |
| --- | --- |
| 문제 | 소스 코드와 테스트가 맞아도 실제 실행 동작은 다를 수 있습니다. |
| 결정 | 앱을 띄우고, 조작하고, 증거를 남기는 절차를 프로젝트 검증 스킬 `.claude/skills/verify-<app>/`로 고정합니다. 만들 때 한 번 끝까지 실행해 동작을 증명합니다. 기능 지도에도 `covers`를 달아 결정 3의 검사 대상에 넣습니다. |
| 비용 | 앱 구동 환경(포트, 브라우저 자동화 등)을 처음에 정리해야 합니다. |

### 6. 버전 표시 기반 증분 업그레이드

| 항목 | 내용 |
| --- | --- |
| 문제 | 스킬이 개선되어도 이미 하네스를 적용한 프로젝트는 그대로 남습니다. |
| 결정 | `CLAUDE.md`에 `<!-- harness-engineering vN -->`, `team-run.js`에 `// team-run template vN`을 둡니다. 줄 번호가 아니라 이 문자열로 버전을 찾습니다. `upgrade.md`는 버전 사이의 변경을 항목별로 기록하고, 항목마다 "이미 반영됐는지 확인하는 방법"을 함께 둡니다. 업그레이드는 남은 항목을 승인받아 하나씩 적용하고 항목마다 커밋합니다. |
| 보완 | 팀 템플릿은 이전 버전을 `templates/archive/`에 보관합니다. 업데이트할 때 프로젝트만의 수정을 찾는 비교 기준으로 씁니다. |
| 비용 | 스킬을 바꿀 때마다 업그레이드 항목을 함께 작성해야 합니다. |

## 에이전트 팀(harness-agent-team)

### 7. 결정적 Workflow 스크립트로 지휘

| 항목 | 내용 |
| --- | --- |
| 문제 | 역할끼리 메시지로 서로 부르는 방식에서는, 역할 정의에 "다음 역할을 부른다"고 적혀 있어도 실제 도구 목록에 호출 수단이 없으면 진행이 조용히 멈춥니다. 지휘자가 판단하지 않는 구조에서는 이 공백을 아무도 메우지 않습니다. |
| 결정 | 하나의 Workflow 스크립트가 정해진 순서대로 역할을 실행합니다. 분기는 역할이 돌려준 구조화된 값(`pass`, `status`, `needsDesign`, `redTeam`, `blocked`)으로만 합니다. 역할끼리는 대화하지 않고, 결과는 작업 파일과 반환값으로만 넘어갑니다. |
| 대안 | `SendMessage` 기반의 역할 간 직접 호출. 유연하지만 진행 보장이 모델 판단에 달려 있습니다. 이 방식도 `references/team-orchestration.md`에 남겨 두고, 사용자가 원할 때만 씁니다. |
| 비용 | 흐름을 바꾸려면 스크립트를 고쳐야 합니다. 조각은 같은 작업 트리를 공유하므로 병렬이 아니라 차례로 진행합니다. |

### 8. 브리프가 없으면 시작하지 않는다

| 항목 | 내용 |
| --- | --- |
| 문제 | 범위가 정해지지 않은 작업은 구현과 검증 기준이 흔들리고, 반려가 반복됩니다. |
| 결정 | 트리아지는 조각마다 목표, 범위, 완료 기준, 검증 방법을 채웁니다. 한 칸이라도 비면 스크립트가 그 조각을 시작하지 않고 보류로 기록합니다. |
| 비용 | 모호한 요청은 첫 실행에서 보류될 수 있습니다. 대신 사람에게 돌아오는 질문이 구체적입니다. |

### 9. 검증은 독립적으로, 수준을 기록한다

| 항목 | 내용 |
| --- | --- |
| 문제 | 검토자가 구현자의 보고를 믿으면 검증이 형식에 그칩니다. "통과"가 무엇을 확인한 결과인지도 알 수 없습니다. |
| 결정 | QA는 항상, 레드팀은 지정된 조각에서 병렬로 판정합니다. 검토자는 완료 기준을 직접 확인하고 확인 수준을 반환합니다(`run`: 실제 실행, `test`: 테스트만, `check`: 정적 검사만). 보고에는 검토자 중 가장 낮은 수준이 남습니다. 배정된 검토자의 결과가 하나라도 없으면 통과로 치지 않습니다. |
| 보완 | 완료 단계에서는 코드를 고치지 않습니다. 검증 뒤에 코드가 바뀌면 검증이 무효가 되기 때문입니다. 커밋까지 성공해야 `done`이고, 검증은 통과했지만 커밋에 실패하면 `verified-uncommitted`로 남깁니다. |

### 10. 보류는 조각 단위로 격리한다

| 항목 | 내용 |
| --- | --- |
| 문제 | 한 조각이 사람의 결정을 기다리는 동안 작업 전체가 멈추면 처리량이 떨어집니다. 보류된 변경이 다음 조각과 섞이면 되돌리기 어렵습니다. |
| 결정 | 조각은 깨끗한 작업 트리에서만 시작합니다. 보류할 때는 그 조각의 변경을 `git stash push -u -m "blocked <조각>"`으로 보관하고, 질문은 `current-state.md`에 남긴 뒤 다음 조각으로 넘어갑니다. 완료나 보류 뒤에 작업 트리가 깨끗하지 않으면 남은 조각은 시작하지 않습니다. |
| 멈춤 기준 | 새 외부 의존성, 검사 자체의 변경, 같은 실패 3회, 외부로 나가는 작업, PRD와 어긋나는 구현, 보안 경계 변경. 보안 경계 변경은 작업 파일의 요청에 사용자 원문 승인이 있으면 진행합니다. |

### 11. 커밋 권한의 분리

| 항목 | 내용 |
| --- | --- |
| 결정 | 커밋은 PRD Maintainer와 doc-gardener만 합니다. 구현자, QA, 레드팀은 커밋하지 않습니다. push, 배포, 서명은 사용자가 따로 요청할 때만 합니다. |
| 이유 | 검증을 거치지 않은 변경이 이력에 들어가지 않습니다. 외부에 영향을 주는 작업은 항상 사람이 결정합니다. |

### 12. 실행 기록 기반의 비대칭 모델 조정

| 항목 | 내용 |
| --- | --- |
| 문제 | 모든 단계에 가장 강한 모델을 쓰면 비용이 큽니다. 반대로 고정된 저가 배정은 품질 문제를 놓칩니다. |
| 결정 | 판단 역할(설계, 레드팀, 회고)은 고정합니다. 품질 기준을 판단하는 역할이 스스로 약해지면 결함을 잡을 수단이 없어지기 때문입니다. 나머지 단계는 실행마다 `problem`, `clean`, `skip`을 기록하고 스크립트 코드가 배정을 계산합니다. 같은 기록에는 항상 같은 결과가 나옵니다. |
| 규칙 | 문제가 생기면 바로 한 단계 올립니다. 내리는 것은 설계가 있었거나 조각이 2개 이상인 실행에서 연속 3회 깨끗할 때만 합니다. 한 번이라도 올라간 적이 있으면 5회가 필요합니다. 같은 단계가 두 번 올라가면 자동 하향을 멈추고 사람이 판단합니다. 하한선과 잠금(`locked`)을 지원합니다. 사용자가 발견한 버그는 다음 실행에서 QA 모델을 바로 올립니다. |
| 비용 | 실행 기록이 쌓이기 전까지는 기본 배정의 비용을 그대로 냅니다. |

### 13. 지시는 파일로 누적한다

| 항목 | 내용 |
| --- | --- |
| 문제 | 사람이 반복한 지시를 프롬프트에 계속 덧붙이면, 프롬프트가 길어지고 역할마다 내용이 어긋납니다. |
| 결정 | 반복된 지시는 `docs/team/standing-orders.md`에 번호를 붙여 한 줄씩 쌓습니다. 모든 역할이 매번 이 파일을 읽습니다. 역할 프롬프트에는 역할 파일 경로, 작업 파일 경로, 지금 할 일만 넣습니다. |
