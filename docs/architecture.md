# 설계 결정과 트레이드오프

두 스킬을 왜 이렇게 만들었는지 정리한 문서입니다. 결정마다 세 가지를 적습니다.

- **문제:** 무엇이 잘 안 됐는가
- **선택:** 어떻게 하기로 했는가
- **대가:** 그 대신 무엇을 포기했는가

낯선 용어(PRD, 레드팀, 훅, stash 등)는 README의 [용어 풀이](../README.md#용어-풀이)에 있습니다.

## 출발점

에이전트는 사람과 다르게 일합니다.

- 지금 연 파일만 봅니다.
- 가장 가까운 예시를 그대로 따라 합니다.
- 컴파일만 되면 가장 짧은 길을 고릅니다.
- 저장소에 없는 정보는 모릅니다. 대화로 알려 준 규칙도 다음 세션에서는 사라집니다.

그래서 이 스킬들은 에이전트를 설득하지 않습니다. 저장소 자체를 바꿔서, 잘못된 변경이 자동으로 실패하게 만듭니다.

## harness-engineering

### 1. `CLAUDE.md`는 짧은 목차로 둔다

**문제:** 지침 파일 하나에 모든 규칙을 넣으면 길어집니다. 길어지면 중요한 규칙이 묻히고, 금방 낡습니다.

**선택:** `CLAUDE.md`는 100~150줄의 목차로 둡니다. 자세한 내용은 `docs/` 아래 주제별 문서에 둡니다. 폴더마다 목차 파일을 둡니다.

**대가:** 문서 수가 늘어 관리할 것이 많아집니다. 이 부담은 결정 3(낡은 문서 찾기)으로 줄입니다.

### 2. 규칙은 가능한 한 높은 수준에서 막는다

**문제:** "~하는 것이 좋다" 같은 문장은 대화가 길어지면 지켜지지 않습니다. 리뷰에서 같은 지적이 반복됩니다.

**선택:** 같은 실수가 두 번 나오면 규칙으로 만듭니다. 아래 순서로 시도하고, 안 될 때만 다음 단계로 내려갑니다.

1. 구조를 바꿔서 실수할 길 자체를 없앤다
2. 타입으로 잘못된 값을 쓸 수 없게 한다
3. 린터, 훅, CI로 막는다
4. 테스트로 잡는다
5. 문서에 적는다(최후의 수단)

새 검사는 과거의 실제 실수를 되살려서, 정말 실패하는지 확인한 뒤에 씁니다. 기존 위반이 많으면 늘어난 것만 실패시킵니다.

**대가:** 처음에 검사를 만드는 시간이 듭니다. 실패 메시지에 고치는 방법까지 적어야 해서 검사 하나를 만드는 데도 손이 갑니다.

### 3. 낡은 문서는 git 기록으로 찾는다

**문제:** 문서가 코드와 달라져도 아무것도 실패하지 않습니다. 낡은 문서는 에이전트에게 틀린 지시가 됩니다.

**선택:** 문서마다 자기가 설명하는 코드 경로를 문서 맨 위의 `covers` 항목에 적습니다. 그 경로가 문서보다 나중에 커밋됐으면 "확인 필요"로 표시합니다. 경로가 사라졌으면 "참조 깨짐"으로 표시합니다.

**대가:** 사소한 코드 변경에도 "확인 필요"가 뜰 수 있습니다. 대신 따로 관리할 색인 파일이 없습니다.

### 4. 세션 인계는 파일 한 장으로 한다

**문제:** 날짜별 인계 파일이 쌓이면 어느 것이 최신인지 모릅니다. 새 세션이 오래된 할 일을 따라갑니다.

**선택:** `docs/plans/current-state.md` 한 장을 매번 덮어씁니다. 내용은 세 가지만 60줄 이하로 적습니다.

- 지금 단계
- 다음 할 일
- 남은 질문

이 형식은 검사로 강제합니다.

**대가:** 지난 인계 내용은 git 기록에서만 볼 수 있습니다.

### 5. 에이전트가 직접 실행해서 확인한다

**문제:** 코드와 테스트가 맞아도 실제로 실행하면 다르게 동작할 수 있습니다.

**선택:** 앱을 띄우고, 조작하고, 결과를 남기는 절차를 프로젝트 전용 스킬(`.claude/skills/verify-<app>/`)로 만듭니다. 만들 때 한 번 끝까지 실행해서 정말 되는지 확인합니다.

**대가:** 처음에 실행 환경(포트, 브라우저 자동화 등)을 정리해야 합니다.

### 6. 업그레이드는 버전 표시로 한다

**문제:** 스킬을 고쳐도 이미 하네스를 적용한 프로젝트는 예전 상태로 남습니다.

**선택:** `CLAUDE.md`와 팀 스크립트에 버전 표시를 둡니다. 업그레이드할 때는 그 버전 이후에 바뀐 항목만 보여 주고, 승인한 항목만 하나씩 반영합니다.

**대가:** 스킬을 고칠 때마다 업그레이드 항목도 함께 적어야 합니다.

## harness-agent-team

### 7. 진행 순서는 스크립트가 정한다

**문제:** 에이전트끼리 메시지로 다음 단계를 부르게 하면 문제가 생깁니다. 다음 담당자를 부를 도구가 없거나 부르는 것을 잊으면, 일이 조용히 멈춥니다.

**선택:** Workflow 스크립트 하나가 정해진 순서대로 역할을 실행합니다. 다음 단계는 각 역할이 돌려준 값(통과, 반려, 보류)으로만 정합니다. 역할끼리는 대화하지 않습니다.

**대가:** 흐름을 바꾸려면 스크립트를 고쳐야 합니다. 작업들은 같은 파일을 건드릴 수 있어서 동시에 돌리지 않고 하나씩 돌립니다.

### 8. 작업 정의가 비어 있으면 시작하지 않는다

**문제:** 범위가 애매한 작업은 구현도 검증도 흔들리고, 반려가 반복됩니다.

**선택:** 작업마다 네 가지를 채웁니다.

- 목표
- 범위
- 완료 기준
- 검증 방법

하나라도 비면 시작하지 않고 보류합니다.

**대가:** 모호한 요청은 처음부터 보류될 수 있습니다. 대신 사람에게 돌아오는 질문이 구체적입니다.

### 9. 검증은 구현자의 말을 믿지 않는다

**문제:** 검토자가 구현자의 보고만 보면 검증이 형식에 그칩니다.

**선택:** QA는 매번, 레드팀은 위험한 작업에서 함께 검증합니다. 검토자는 완료 기준을 직접 확인하고, 어디까지 확인했는지 남깁니다.

- `run`: 실제로 실행해 봤다
- `test`: 테스트만 돌렸다
- `check`: 코드만 읽었다

검토자 중 한 명이라도 결과를 내지 않으면 통과로 치지 않습니다. 검증이 끝난 뒤에는 코드를 고치지 않습니다.

**대가:** 검토자가 여럿이라 시간과 비용이 더 듭니다.

### 10. 막힌 작업만 멈춘다

**문제:** 한 작업이 사람의 답을 기다리는 동안 전체가 멈추면 느려집니다. 멈춘 작업의 변경이 다음 작업과 섞이면 되돌리기 어렵습니다.

**선택:** 작업은 항상 깨끗한 상태에서 시작합니다. 멈출 때는 그 작업의 변경만 따로 보관(`git stash`)하고, 질문을 남긴 뒤 다음 작업으로 넘어갑니다.

아래 경우에는 반드시 멈추고 사람에게 묻습니다.

- 새 외부 의존성 추가
- 검사 규칙 자체를 바꾸는 변경
- 같은 실패 3번 반복
- 배포, 서명, push처럼 외부로 나가는 작업
- 제품 요구 사항과 어긋나는 구현
- 인증, 권한, 네트워크 노출 같은 보안 관련 변경

**대가:** 보류된 작업이 쌓이면 사람이 한 번에 답해야 할 질문이 늘어납니다.

### 11. 커밋은 두 역할만 한다

**선택:** 커밋은 PRD Maintainer와 doc-gardener만 합니다. 구현자, QA, 레드팀은 커밋하지 않습니다. push와 배포는 사람이 요청할 때만 합니다.

**이유:** 검증을 거치지 않은 변경이 기록에 들어가지 않습니다. 밖으로 나가는 일은 항상 사람이 정합니다.

### 12. 모델은 실행 결과를 보고 조정한다

**문제:** 모든 단계에 가장 강한 모델을 쓰면 비용이 큽니다. 처음부터 싼 모델로 고정하면 품질 문제를 놓칩니다.

**선택:**

- 설계, 레드팀, 회고는 항상 강한 모델로 고정합니다. 품질을 판단하는 역할이 약해지면 문제를 잡을 수단이 없어지기 때문입니다.
- 나머지 단계는 실행 결과에 따라 바뀝니다.
  - 문제가 생기면 바로 한 단계 올립니다.
  - 충분히 큰 작업에서 3번 연속 문제가 없을 때만 한 단계 내립니다.
  - 한 번 올라간 적이 있으면 5번 연속이어야 내립니다.
  - 같은 단계가 두 번 올라가면 자동으로 내리지 않고 사람이 정합니다.
- 계산은 스크립트가 합니다. 같은 기록이면 항상 같은 결과가 나옵니다.

**대가:** 기록이 쌓이기 전까지는 기본 배정 비용을 그대로 냅니다.

### 13. 반복된 지시는 파일에 쌓는다

**문제:** 사람이 같은 지시를 반복할 때마다 프롬프트에 덧붙이면, 프롬프트가 길어지고 역할마다 내용이 달라집니다.

**선택:** 반복된 지시는 `docs/team/standing-orders.md`에 한 줄씩 쌓습니다. 모든 역할이 매번 이 파일을 읽습니다.

**대가:** 파일이 길어지면 사람이 가끔 정리해야 합니다.
