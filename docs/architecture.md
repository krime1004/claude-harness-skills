# 설계 결정과 트레이드오프

README의 네 원칙을 어떻게 구현했는지, 그 대가로 무엇을 포기했는지 정리한다. 결정마다 세 가지를 적는다.

- **문제:** 무엇이 잘 안 됐는가
- **선택:** 어떻게 구현했는가
- **대가:** 무엇을 포기했는가

## 출발점

에이전트는 사람과 다르게 일한다.

- 지금 연 파일만 본다.
- 가장 가까운 예시를 그대로 따라 한다.
- 컴파일되는 가장 짧은 길을 고른다.
- 저장소에 없는 정보는 모른다. 대화로 전한 규칙은 다음 세션에서 사라진다.

그래서 에이전트를 설득하지 않는다. 판단은 에이전트에게 맡기되, 결정은 코드와 검사가 내리도록 저장소를 설계한다.

## 1. 목표를 먼저 정의한다

### 1.1 정의되지 않은 작업은 시작하지 않는다

**작업 정의는 구현의 전제 조건이다.**

- **문제:** 범위가 애매한 작업은 구현도 검증도 흔들린다. 반려가 반복되고, 무엇이 완료인지 아무도 모른다.
- **선택:** 트리아지는 작업마다 목표, 범위, 완료 기준, 검증 방법을 채워 스키마로 돌려준다. 한 칸이라도 비면 스크립트가 시작을 거부하고 보류로 기록한다. 구현은 테스트를 먼저 쓰고, 완료 기준을 통과하는 것으로 끝난다.
- **대가:** 모호한 요청은 첫 실행에서 보류될 수 있다. 대신 사람에게 돌아오는 질문이 구체적이다.

## 2. 증거로 통과시킨다

### 2.1 검토자는 직접 확인하고 수준을 남긴다

**판정에는 증거와 확인 수준이 함께 있어야 한다.**

- **문제:** 검토자가 구현자의 보고만 보면 검증이 형식에 그친다. "통과"가 무엇을 확인한 결과인지도 알 수 없다.
- **선택:** QA는 매번, 레드팀은 위험한 작업에서 병렬로 검증한다. 판정 스키마는 `pass`, `level`, `evidence`, `findings`를 필수로 요구한다. 확인 수준은 `run`(실제 실행), `test`(테스트), `check`(정적 검사)이며, 검토자 중 가장 낮은 수준이 보고에 남는다. 배정된 검토자가 한 명이라도 응답하지 않으면 통과가 아니다.
- **대가:** 검토자가 여럿이라 시간과 비용이 더 든다.

### 2.2 검증이 끝나면 코드는 고정된다

**검증 이후의 수정은 검증을 무효로 만든다.**

- **문제:** 완료 처리 중에 코드를 조금 고치면, 검증받지 않은 변경이 완료로 기록된다.
- **선택:** 완료 단계는 코드를 고치지 않고 문서와 기록만 갱신한다. 커밋까지 성공해야 `done`이다. 검증은 통과했지만 커밋에 실패하면 `verified-uncommitted`로 따로 남긴다.
- **대가:** 완료 단계에서 발견한 사소한 문제도 다음 작업으로 넘겨야 한다.

### 2.3 실행해서 확인한다

**코드를 읽는 것만으로는 동작을 증명할 수 없다.**

- **문제:** 코드와 테스트가 맞아도 실제로 실행하면 다르게 동작할 수 있다.
- **선택:** 앱을 실행하고, 조작하고, 증거를 남기는 절차를 프로젝트 전용 검증 스킬(`.claude/skills/verify-<app>/`)로 고정한다. 만들 때 한 번 끝까지 실행해 동작을 증명한다.
- **대가:** 처음에 실행 환경(포트, 브라우저 자동화 등)을 정리해야 한다.

## 3. 결정은 코드가 한다

### 3.1 진행 순서는 스크립트가 정한다

**에이전트는 판단하고, 스크립트가 결정한다.**

- **문제:** 에이전트끼리 메시지로 다음 단계를 부르게 하면, 호출 도구가 없거나 부르는 것을 잊을 때 작업이 알림 없이 멈춘다.
- **선택:** Workflow 스크립트 하나가 정해진 순서대로 역할을 실행한다. 모든 역할은 JSON 스키마로만 결과를 돌려주고, 다음 단계는 그 값(`pass`, `status`, `needsDesign`, `redTeam`, `blocked`)으로만 정한다. 역할끼리는 대화하지 않는다.
- **대가:** 흐름을 바꾸려면 스크립트를 고쳐야 한다. 작업들은 같은 파일을 건드릴 수 있어 하나씩 순서대로 실행한다.

### 3.2 막힌 작업만 멈춘다

**사람의 결정이 필요한 작업만 격리하고, 나머지는 계속한다.**

- **문제:** 한 작업이 답을 기다리는 동안 전체가 멈추면 느려진다. 멈춘 작업의 변경이 다음 작업과 섞이면 되돌리기 어렵다.
- **선택:** 작업은 항상 깨끗한 작업 트리에서 시작한다. 반려가 3회를 넘거나 멈춤 기준에 걸리면 그 작업의 변경만 `git stash`로 보관하고, 질문을 남긴 뒤 다음 작업으로 넘어간다. 멈춤 기준은 다음과 같다.
  - 새 외부 의존성 추가
  - 검사 규칙 자체를 바꾸는 변경
  - 같은 실패의 3회 반복
  - 배포, 서명, push처럼 외부로 나가는 작업
  - 제품 요구 사항과 어긋나는 구현
  - 인증, 권한, 네트워크 노출 같은 보안 관련 변경
- **대가:** 보류된 작업이 쌓이면 사람이 한 번에 답해야 할 질문이 늘어난다.

### 3.3 모델 배정은 실행 기록으로 계산한다

**같은 기록이면 항상 같은 배정이 나온다.**

- **문제:** 모든 단계에 가장 강한 모델을 쓰면 비용이 크다. 처음부터 저렴한 모델로 고정하면 품질 문제를 놓친다.
- **선택:** 설계, 레드팀, 회고처럼 품질을 판단하는 역할은 가장 강한 모델로 고정한다. 나머지 단계는 실행 결과를 `problem`, `clean`, `skip`으로 기록하고 스크립트가 배정을 계산한다.
  - 문제가 반복되면 바로 한 단계 올린다.
  - 큰 작업에서 3회 연속 문제가 없을 때만 한 단계 내린다. 한 번 올라간 적이 있으면 5회가 필요하다.
  - 같은 단계가 두 번 올라가면 자동 하향을 멈추고 사람에게 넘긴다.
- **대가:** 기록이 쌓이기 전까지는 기본 배정의 비용을 그대로 낸다.

### 3.4 커밋은 두 역할만 한다

**검증을 거치지 않은 변경은 기록에 들어가지 않는다.**

- **선택:** 커밋은 PRD Maintainer와 doc-gardener만 한다. 구현자, QA, 레드팀은 커밋하지 않는다. push와 배포는 사람이 요청할 때만 한다.
- **대가:** 구현 중간 상태는 커밋으로 남지 않는다.

## 4. 규칙은 검사로 강제한다

### 4.1 가장 높은 수준에서 막는다

**문서에만 있는 규칙은 지켜지지 않는다.**

- **문제:** "~하는 것이 좋다" 같은 문장은 대화가 길어지면 무시된다. 리뷰에서 같은 지적이 반복된다.
- **선택:** 같은 실수가 두 번 나오면 규칙으로 만들고, 아래 순서로 가장 높은 수준에서 막는다.
  1. 구조: 실수할 경로 자체를 없앤다
  2. 타입: 잘못된 값을 표현할 수 없게 한다
  3. 린터·훅·CI: 컴파일되는 실수를 차단한다
  4. 테스트: 동작 회귀를 잡는다
  5. 문서: 판단이 필요한 경우에만 쓴다

  새 검사는 과거의 실제 실수를 되살려 실패하는 것을 확인한 뒤에 채택한다. 기존 위반은 기준선으로 묶고 늘어나는 것만 막는다. 예외에는 사유, 만료일, 승인자를 남긴다.
- **대가:** 검사를 만드는 초기 비용이 크다. 실패 메시지에 고치는 방법까지 적어야 한다.

### 4.2 낡은 문서는 git 기록으로 찾는다

**문서가 코드보다 오래되면 저장소가 먼저 알린다.**

- **문제:** 문서가 코드와 달라져도 아무것도 실패하지 않는다. 낡은 문서는 에이전트에게 틀린 지시가 된다.
- **선택:** 문서마다 설명하는 코드 경로를 `covers`에 선언하고, 선언은 훅으로 강제한다. 그 경로가 문서보다 나중에 커밋됐으면 "확인 필요", 경로가 사라졌으면 "참조 끊김"으로 표시한다.
- **대가:** 사소한 코드 변경에도 "확인 필요"가 표시될 수 있다. 대신 따로 관리할 색인이 없다.

### 4.3 세션 인계 형식도 검사한다

**새 세션의 시작점은 한 장이다.**

- **문제:** 날짜별 인계 파일이 쌓이면 어느 것이 최신인지 모른다. 새 세션이 오래된 할 일을 따라간다.
- **선택:** `docs/plans/current-state.md` 한 장을 덮어쓴다. 지금 단계, 다음 할 일, 대기 중인 질문만 60줄 이하로 적는다. 날짜별 인계 파일 금지, 줄 수, 진입점 링크는 검사 스크립트로 강제한다.
- **대가:** 지난 인계 내용은 git 기록에서만 볼 수 있다.

## 기반: 저장소가 기억한다

### 지도와 기록을 분리한다

**`CLAUDE.md`는 매뉴얼이 아니라 지도다.**

- **선택:** `CLAUDE.md`는 100~150줄의 목차로 두고, 자세한 내용은 `docs/` 아래 주제별 문서에 둔다. 진행 중 작업, 결정 로그, 완료 이력도 모두 파일로 남긴다.
- **대가:** 문서 수가 늘어난다. 이 부담은 4.2(낡은 문서 찾기)로 관리한다.

### 반복된 지시는 파일에 쌓는다

**프롬프트를 늘리지 않고, 지시를 파일로 누적한다.**

- **선택:** 사람이 반복한 지시는 `docs/team/standing-orders.md`에 한 줄씩 쌓고, 모든 역할이 매번 읽는다. 역할 프롬프트에는 역할 파일, 작업 파일, 지금 할 일만 넣는다.
- **대가:** 파일이 길어지면 사람이 가끔 정리해야 한다.

### 개선은 버전으로 전파한다

**한 번 고치면 모든 프로젝트가 따라온다.**

- **선택:** `CLAUDE.md`와 팀 스크립트에 버전 표시를 둔다. 업그레이드는 그 버전 이후 바뀐 항목만 보여 주고, 승인한 항목만 하나씩 반영해 커밋한다. 이전 템플릿을 보관해 두어, 프로젝트마다 직접 고친 부분은 덮어쓰지 않고 구별한다.
- **대가:** 스킬을 고칠 때마다 업그레이드 항목도 함께 적어야 한다.
